# Yvoke-Web — Claude Code Project Rules

This project enforces Spec-Driven Development and strict architectural patterns.
These rules **override** default behavior. Follow them exactly.

> This file is the Claude Code equivalent of `.agents/AGENTS.md`. The two are kept
> in sync intentionally — if you change a rule here, mirror it there (and vice versa).

## 1. Universal Hard Rules (apply to ALL tasks)

- **Do NOT commit or merge**: Never commit, push, or merge via Git. The user reviews and commits manually. Leave changes uncommitted in the working tree. The same applies to release tags: never create, move or push one. Releases are cut by the Release workflow, which the user triggers from GitHub; it resolves the version, pins it into the k8s manifest, verifies, commits and tags in one place, so an agent tagging by hand would produce exactly the split that design exists to prevent. See README `## Releasing`.
- **Testing & TDD**: Use strict TDD (Red → Green → Refactor). Integration tests MUST end with `*IT.java` and live in `src/it/java`, mirroring the source package structure. Run integration tests via `./mvnw verify -Pit-tests` (requires a running Docker daemon).
- **Regression testing**: When a bug is discovered, first write a failing test (unit or integration) that reproduces it, then fix it.
- **A test does not count until you have seen it fail**: after writing or changing a test, break the *one specific thing it claims to pin* with a minimal edit to production code, run it, watch it go **red**, then restore — by re-reading the original, never from memory, since a whole-file restore silently reverts a sibling mutation and the "green" run afterwards proves nothing. A test that has only ever been green is a claim, not evidence, and a brand-new test that passes on its **first** run against code you have not yet fixed is a defect in the test, not luck. Six entries in *Known Pitfalls* are bugs that an existing, passing test was actively hiding; read them there rather than trusting that coverage implies enforcement.
- **Confirm the change is actually running before you trust a result**: the edit is made, the tool reports success, and the change is not live — five entries in *Known Pitfalls* are that one shape, covering the container stack, the compiler's up-to-date check and orphaned builds. So assert the precondition instead of assuming it (the schema version, that the test *count* changed, that no second build is running), and never read a bare `BUILD SUCCESS` as proof new code ran. Always `set -o pipefail`: a pipeline reports its **last** command's status, so a failing build behind `| tail` exits 0.
- **Prefer making the bug unrepresentable over fixing it**: when the fix is in, ask what parameter, branch or overload can now be **deleted** so the mistake cannot be re-expressed — an argument that no longer exists needs no rule, no comment and no reviewer. This is the only form of guidance a future agent cannot skip, misread or fail to load, so reach for it before reaching for prose.
- **Flyway migrations**: SQL scripts go in `docker/db/migration/` using sequential naming `V<N>__<name>.sql`. Never modify an existing migration script.
- **Vertical domain packaging**: Group Java code by domain slice under `de.palsoftware.yvoke` (never horizontal/layer-first). The dependency invariants are enforced by `ArchitectureTest.java` (ArchUnit) and fail the build on regression:
  - `shared` must not depend on **any** domain package (it is cross-cutting infrastructure only).
  - A domain's `core` must not depend on that domain's `api`/`web` (presentation depends on core, never the reverse).
  - Controllers (`@Controller`/`@RestController`) live only in `..api..`, `..web..`, or `..security..`.
  - Domain slices must be free of cycles.
  - Note: cross-domain dependencies between domains ARE allowed — a legitimate cross-domain orchestrator (e.g. `lifecycle.core`) may depend on multiple domains. Do not "fix" a domain→domain dependency unless `ArchitectureTest` actually fails.
- **DTOs at the boundary**: The service layer maps DB entities/records to DTOs before returning to the web/UI layer. Raw entities must not leak into Thymeleaf templates.
- **No inline config defaults**: Define all defaults in `application.yml`. Never use inline defaults in `@Value` (no `@Value("${x:default}")`).
- **No fully-qualified class names inline**: Add an `import` at the top of the file and use the simple name (e.g. `AtomicInteger`, not `java.util.concurrent.atomic.AtomicInteger`). Enforced by `NoInlineFullyQualifiedNamesTest`, which scans source text — ArchUnit cannot see this, since both forms compile to identical bytecode. Comments, javadoc, strings and text blocks are exempt; if a simple name genuinely collides with another import, add the file to that test's `ALLOWED` map with the reason.
- **No assumptions**: If requirements are ambiguous, use the `AskUserQuestion` tool to present multiple-choice options before proceeding. Do not guess on design intent.
- **The tests are the behaviour contract**: there is no prose specification of internal behaviour, deliberately — one existed and was retired once the test suite carried it, because a document nothing executes drifts from the code and is then worse than nothing, since agents act on it. Before changing a feature, read the tests that own it; to change behaviour, change a test. **If no test fails when you break a rule, that rule is not enforced** — treat it as undocumented rather than assuming it is safe, and pin it with a test in the same change. The retired document was itself called `spec.md`, so note that **today's `spec.md` (repo root) is not it**: it is the *functional* specification — what the system does, its limits, and what it deliberately does not do. **Before a substantial change, read its chapter for the area you are touching**, then the tests that own the feature: the chapter gives you intent and deliberate non-features, the tests give you the contract. Keep it true — a change a user would notice updates that chapter in the same change set, **Limits** / **Not supported** included, since intentional absences are what no test can fail on.
- **Self-learning**: When you hit a non-obvious pitfall or key architectural insight, record it so it isn't repeated — in § 6 *Known Pitfalls* of **both** this file **and** `.agents/AGENTS.md`, word for word (`AgentRuleFilesParityTest` fails the build if they diverge, or if a pitfall is also restated outside § 6), or in the relevant `.antigravity/steering/` doc.

## 2. Engineering Standards (security · performance · maintainability)

Apply to **all** code, not just large tasks. Get it right while writing — do not defer to review.

**Security** — this is an AI/RAG app; treat request params, ingested corpus (Confluence/manuals), and LLM output as **tainted input**:
- **Parameterized SQL only.** Bind values with `JdbcClient` named/positional params. Never concatenate or interpolate request/corpus/LLM-derived values into SQL — including dynamic `ORDER BY`/`LIMIT` (whitelist those against a fixed set).
- **Authorize every entry point.** Gate controllers/endpoints in the **`SecurityConfig` filter chain**, or with an explicit guard called from the handler; deny by default. **Do NOT use `@PreAuthorize`/`@Secured`/`@RolesAllowed`** — there is no `@EnableMethodSecurity` anywhere, so those annotations are *silently inert*: the method runs for everyone while the code, the review and the reader all believe it is gated. `ArchitectureTest` fails the build on them (the rule is conditional — a future change may enable method security, but must add `@EnableMethodSecurity` in the same change). Enforce the caller's ownership of the data they touch — never trust an id straight from the request.
- **Validate at the boundary.** `@Valid` + Bean Validation on all external input (REST DTOs, form posts, MCP tool args). Reject bad input; don't sanitize-and-hope.
- **Never expose secrets.** No credentials/API keys/PII in code, logs, error messages, or templates. Secrets come from env / `application.yml` placeholders only.

**Performance:**
- **No N+1.** One round-trip: batch or join in SQL; never loop a query per row.
- **Index what you filter/sort/join** — especially every FK. Use the pgvector / ParadeDB BM25 indexes on retrieval paths.
- **Read paths are `@Transactional(readOnly = true)`;** keep transactions narrow — no LLM/HTTP calls inside a DB transaction.
- **Stream, don't block.** LLM/large responses over SSE; paginate list endpoints; respect `app.worker.concurrency` for background work.
- **Cache deliberately.** `@Cacheable` (Caffeine) only for hot, stable reads, with a defined eviction key/policy.

**Maintainability:**
- Smallest change at the root cause; no speculative abstraction or "for later" config knobs.
- Names carry intent; comments explain **why**, not what; match surrounding style.
- Cross-cutting infra lives in `shared`; domain logic never does.

## 3. Tech Stack & Local Workflow

- **Backend**: Spring Boot (Java 25), PostgreSQL. Use `JdbcClient` for data access — **no ORMs**.
- **Frontend**: Thymeleaf + htmx + Vanilla CSS. **No Tailwind.**
- **Layering**: Controllers → Services → Repositories. Respect existing packages.
- **Run locally**: `./redeploy.sh` starts the app at `http://localhost:8080`. View errors with `docker compose logs app`.
- **Frontend debugging**: Drive the local server with the browser tools against `http://localhost:8080`.
- **Test tiers** (these bullets are the command reference; `docs/testing-plan.md` has the design rationale and gotchas, but `docs/` is git-ignored and local-only, so do not assume it is present):
  - `./mvnw test` — unit tests only (fast, no Docker). Also runs the **JS tier** (below).
  - **JS tier** — `node --test src/test/js/*.test.js` (or `npm test`). Pure browser-side logic extracted out of `thread.js` and the admin templates into `static/js/chat/` and `static/js/admin/`, plus a **syntax gate** that parses every app-owned `.js` file *and* every inline `<script>` in every Thymeleaf template — Spotless is Java-only, so without it a JS syntax error reaches production. Tested with `node:test`, **zero dependencies** (no `npm install` — the root `package.json` exists only to declare `type: module` and the script). Bound to the `test` phase via `exec-maven-plugin`; skip with `-DskipJsTests=true`. Put string→string rendering logic here, not in e2e: it is ~1000× faster, and browser e2e **cannot** cover mermaid/KaTeX at all (both are CDN-only in `chat/layout.html` and `AbstractE2E` aborts every non-localhost request, so a diagram assertion passes whether the source is intact or destroyed).
  - `./mvnw verify -Pit-tests` — unit + integration (Testcontainers Postgres; **excludes** browser e2e). Emits the aggregated JaCoCo report (`target/site/jacoco-aggregate`) and enforces the **coverage ratchet** (fails if the merged aggregate drops below the floor). Add `-DskipUnitTests=true -Dit.test=Foo` to run one IT fast.
  - `./mvnw verify -Pe2e-tests` — Playwright browser e2e (`*E2EIT`, extend `AbstractE2E`); first run downloads Chromium to `~/.cache/ms-playwright`.
- **Mocking the LLM in tests**: replace the **provider** bean — `@MockitoBean(name = "llmProviderClient") LlmClient` — the **provider** bean, not the `@Primary` `LlmClient`, which is the `AccountingLlmClient` decorator; mocking the primary would replace cost accounting along with the provider — with `doAnswer(...)` feeding `LlmResponseChunk`s drives the whole rendered answer deterministically (no network, provider-agnostic). Browser e2e call `AbstractE2E.stubAssistantReply("…")` for a one-line scripted answer; a *blocking* `doAnswer` (latch + `Thread.sleep` → `CancellationException`) is needed to test stop/cancel. Do **not** use WireMock for answer simulation.

## 4. Task Routing

- **Small / medium tasks**: Execute directly. No planning artifacts required.
- **Large tasks / features / refactors**: Use the Spec-Driven Development flow — run `/sdd` (see `.claude/commands/sdd.md`) or read `.antigravity/sdd_protocol.md`.
- **Subagents** (invoke via the Agent tool):
  - `spring-implementer` — writes local Spring Boot / Postgres / Thymeleaf code.
  - `spring-reviewer` — read-only audit for security, transactions, migrations, N+1.
  - Only **one** code-writing subagent should be active at a time.

## 5. Deep Context & Steering

**`spec.md` (repo root) is the functional specification** — eight capability chapters, each with *What
you can do* / *How it behaves* / *Limits* / *Not supported*. It governs *what the product does*. **Start
a substantial change by reading its chapter for the area you are touching**: it is the fastest way to
learn what a feature is for, which behaviours are deliberate, and what the product has decided not to
do. The **Limits** and **Not supported** sections are load-bearing — they record intentional absences,
and an absence is exactly what no test can fail on. It is not a technical specification and must not
become one; it says what the product does, never how it is built.

**The test suite is the behaviour contract.** `./mvnw verify -Pit-tests` is what enforces it; every rule
worth preserving has a test that fails when it is broken. So: the spec chapter for *intent*, then the
tests that own the feature for the *contract*, both read *before* changing it. This file (CLAUDE.md)
governs *how to build*.

For large tasks or architectural decisions, also read the steering docs:
- `.antigravity/steering/tech.md` — tech stack details.
- `.antigravity/steering/structure.md` — directory & package layout.
- `.antigravity/steering/product.md` — domain glossary.

After structural changes (migrations, `pom.xml`, config, new packages), run
`python3 .antigravity/scripts/check_steering.py` and update the steering docs if it flags drift.

`spec.md` is exempt from the "no spec files in the workspace" rule — that rule targets *transient
per-task planning artefacts* (implementation plans, task checklists, walkthroughs), which still stay out
of the working tree. `spec.md` is a durable product artefact; do not delete it as clutter.

## 6. Known Pitfalls (project-specific)
Accumulated, hard-won gotchas. Several exist specifically because the obvious diagnosis was the wrong
one — read this section before debugging a build or test failure that makes no sense.

**This list is a FULL MIRROR of `.agents/AGENTS.md` § 6, not a pointer.** The two files are the same
rules for two different agent toolchains, and an agent that loads only one of them must not be missing a
pitfall. Add every new entry to BOTH, verbatim, and to this section only — `AgentRuleFilesParityTest`
fails the build when they diverge, and also when a pitfall is restated outside § 6, which is how a stale
second copy went unnoticed above `AGENTS.md` § 6 for as long as it did.


- **Mock `HttpServer` tests**: Bind explicitly to `new InetSocketAddress("127.0.0.1", 0)` and consume `exchange.getRequestBody().readAllBytes()` before responding — otherwise you get flaky socket-closure / 400 errors from unconsumed request bodies.
- **LLM call context & FK constraints**: When logging sub-calls (embeddings/reranks/tools) during an in-flight LLM turn, set `LlmCallContextHolder` with the already-persisted `userMessageId` to avoid `fk_llm_call_logs_messages` FK violations before the assistant message exists.
- **Background-thread user resolution**: Background / virtual threads have no `SecurityContext`. Resolve `user_id` via `conversationRepository.findById(convId).map(Conversation::userId)`, not `SecurityContextHolder`.
- **Thymeleaf inline-JS script order**: In templates with `th:inline="javascript"`, declare all `const`/`let` (DOM selectors, state arrays) near the top of the script block, before any top-level function invocation — otherwise page init throws a Temporal Dead Zone (TDZ) `ReferenceError`.
- **Dev-profile is required for mock auth & plaintext secrets (fail-closed)**: `app.security.mock=true` and running without `APP_SECRET_KEY` are only permitted when a `dev`/`local`/`test` profile is active (`SecurityConfig`/`SecretCipher` throw at startup otherwise — SEC-09/SEC-05). The IT harness activates `test` via `PostgresTestContainerInitializer`; local `docker-compose` sets `SPRING_PROFILES_ACTIVE=local`. A new `@SpringBootTest` in `src/it` inherits `test` automatically; a full-context test elsewhere with `mock=true` must set the profile itself.
- **`@Component` with two constructors won't autowire**: If a bean exposes both a `@Value`/production constructor and a package-private test-seam constructor, annotate the production one with `@Autowired` — otherwise Spring can't choose and fails context startup with "No default constructor found" (only surfaces in ITs, not plain unit tests, so always run `./mvnw verify -Pit-tests` after adding such a class).
- **`@ControllerAdvice(annotations = Controller.class)` also matches `@RestController`**: `@RestController` is meta-annotated with `@Controller`, so an MVC-only advice selected by `annotations = Controller.class` (e.g. `MvcExceptionHandler`) is *also* applicable to REST controllers and would compete with the JSON `ApiExceptionHandler`. Give the REST advice higher precedence (`@Order(Ordered.HIGHEST_PRECEDENCE)`) so it wins for `@RestController`s; the MVC advice (`LOWEST_PRECEDENCE`) then only reaches plain `@Controller`s. When a global MVC error advice redirects, gate it to *classic browser form posts* (state-changing method + `Accept: text/html` + no `HX-Request`/`X-Requested-With`) and re-throw everything else, or it will hijack htmx fragments, `void`/`@ResponseBody` fetch endpoints, downloads and GET renders. Re-emit `ResponseStatusException` via `response.sendError(status, reason)` (don't let the generic `Exception` handler swallow it) so a 404 stays a 404 instead of becoming a redirect.
- **IT context-cache thrash poisons the `RANDOM_PORT` MCP context**: The `src/it` suite has more distinct `@SpringBootTest` contexts than Spring's default TestContext cache (`maxSize=32`). Adding an IT whose config is *distinct* (a new `properties`/`@MockitoBean`/mock-bean combination mints a new context) tips it over; LRU eviction + recreation of `McpServerEndpointsIT`'s `RANDOM_PORT` context leaves the spring-ai MCP server poisoned — the JSON-RPC `initialize` POST returns **400**. Diagnostic tell: the new IT passes **alone and in pairs**, but the *full* `./mvnw verify -Pit-tests` fails in an **unrelated** `RANDOM_PORT` IT. Fix is `src/it/resources/spring.properties` → `spring.test.context.cache.maxSize=64`. When adding ITs, prefer **reusing an existing context** (identical annotations/properties/mock beans) over minting a new one; if a full-suite failure surfaces in an unrelated `RANDOM_PORT` IT, suspect cache size, not that IT.
- **All ingest staging must live under `app.upload-dir`**: the worker-side `UploadPathGuard` rejects any job `sourceRef` outside `app.upload-dir`, so staging an upload with `Files.createTempDirectory(...)` (system tmp) makes the job fail at *execution* time with "sourceRef resolves outside the permitted upload directory" — the enqueue succeeds, so nothing surfaces until the worker runs. Stage with `Files.createTempDirectory(Path.of(uploadDir)…, prefix)` and pin it with a unit test asserting the enqueued `sourceRef` starts with the upload root.
- **Ingest tags are silently dropped when the target collection declares no tags**: `CollectionTagEnqueueValidator` only validates/propagates the request's `tag` when `collections.tags` is non-empty — against a collection created with `tags='{}'` the job runs untagged, documents lose version scoping, and a second version's ingest *replaces* the first (same `source_file` keys). Declare the allowed tags on the collection (e.g. `{9.3.1,10.0}`) *before* the first ingest.
- **Graph identity is `(collection, kind, lower(name), tag set)` — the tag is part of it (the unique index lives in `V1__init_schema.sql`; the standalone migration that introduced it was folded in, so today's `V2` is unrelated)**: the OIM corpus keeps two kit versions in ONE collection separated only by tag. While identity was tag-blind, the second version's ingest resolved every same-named entity to the FIRST version's row, `appendTags`'d its tag onto it and inserted nothing; since the per-version document link lives in `entities.metadata->>'document_id'` and nothing ever UPDATEd an existing row, **9,431 of 10.0's 9,904 entities kept pointing at 9.3.1's documents** while the job reported 9,904 written. The read paths were never wrong — they already filter `:tag = ANY(tags)` — the shared row simply carried both tags and had one document_id to give. Consequences to respect: the unique index is over `kg_canonical_tags(tags)` (an IMMUTABLE `COLLATE "C"` sort/dedup, so array ORDER can never fork one scope into two) and every `ON CONFLICT` must name that exact expression; `KgWriteRepository.entityKey` deliberately stays two-part `kind:name` because three call sites parse it positionally (one upsert call = one tag set = one scope); **never reintroduce `appendTags`** — welding a second tag onto an existing row IS the bug; `KgConsolidator` must keep `kg_canonical_tags(e.tags)` in its GROUP BY and edge-collapse PARTITION BY, or it re-merges the split and hard-DELETEs one row, cascading its edges away; and a name+kind without a tag is now ambiguous exactly like a name without a kind, so ordering must be total and the MCP tools return the candidate versions instead of merging them.
- **Re-ingest orphans an entity's `document_id` unless the upsert refreshes it**: `CustomIngestService` deletes and recreates every document with a NEW uuid on each run, but entity rows survive. `upsertEntitiesBatch` had no update branch at all, so a re-ingested collection's entities pointed at deleted documents. `refreshResolved` now writes `metadata`/`description`/`embedding` onto rows resolved in the same tag scope, with `COALESCE` so the LLM path (`DocumentIngestService.persistGraph`, 3-arg `EntityUpsert` with null metadata) cannot wipe the document link the custom path wrote.
- **Graph/document identity is `(collection, kind, name)` — a name alone is ambiguous**: in `OIM - Custom - Install Kit` ~945 entity names and ~900 document titles exist under two to five kinds (`Person` is a `table`, an `entity_model`, `ui_forms`, `object_methods` *and* a `notification`; a REST provider's full name is usually both an `api` and an `api_server`; every colliding connector name also names a `module`). Consequences to respect in any name-based lookup: order rows by a **total** order (a name+similarity tie is otherwise resolved non-deterministically by Postgres, so the caller silently gets a different `document_id` per call), surface `kind` in every tool output, and make an ambiguous lookup fail loudly rather than merging kinds (`get_graph_neighbors` returns the candidate kinds + edge counts instead of edges when no `kind` is given). Prompts/playbooks must pass `kind` alongside `entity_name` and take `document_id` from the row with that kind.
- **Custom (jsonl) ingest fails the job; kg-extract only reports**: `CustomIngestService` now THROWS `IllegalStateException` (which `JobService` turns into the job's `error`, so it reaches the user) on unparseable YAML frontmatter, on any graph entity that resolves to no document, and on an unresolvable edge endpoint (unknown / ambiguous-across-kinds / malformed record) — each message names the offenders, capped at the first 20 plus a total. The trigger was real: a `display_name: %Globals...%` starts a plain YAML scalar with the reserved `%` indicator, so the frontmatter failed to parse, the document silently degraded to `kind='other'`, and its `table` entity ended up with **no `document_id`** for two full re-ingests. `DocumentIngestService.persistGraph` (LLM extraction) deliberately does NOT throw — its entities always come from the document being ingested, and one stray model-invented name must not kill a whole kg-extract job — so it reports the loss instead via `JobCounts.skippedEntities/skippedEdges` (persisted as `ingestion_jobs.skipped_entity_count`/`skipped_edge_count`, defined in `V1__init_schema.sql`, shown on the job-detail page). When adding a new fixture zip to `CustomIngestServiceIT`, give **every** entity in `graph/entities.jsonl` a markdown file with matching `kind`+`name`, or the job legitimately fails.
- **A `<script type="module">` is deferred, so a classic inline script cannot call into it at load time**: the admin pages keep classic inline scripts (their runtime-cloned `<template>` rows carry inline `on*=` handlers that resolve globally and break under module scope), and extracted logic is bridged in via a tiny module script that assigns `window.X`. Module scripts are **always deferred** — they execute *after* every classic script but *before* `DOMContentLoaded`. So a top-level `togglePrompts();` at the end of the classic script runs while `window.IngestForm` is still `undefined` and throws `TypeError: Cannot read properties of undefined`. Function *definitions* and event handlers are fine (they run later); only immediate init calls break. Fix: wrap the init call in `document.addEventListener('DOMContentLoaded', …)`. Check for this with `grep -nE '^ {4,12}[a-zA-Z_$][a-zA-Z0-9_$]*\([^)]*\);[[:space:]]*$'` on the template before extracting — `ingest.html` and `job-detail.html` both had one. `AdminPagesConsoleE2EIT` catches it (it asserts no uncaught JS errors across every admin page), but only if the page is in its list.
- **Bracketed text is not automatically a citation — over-matching deletes the user's prose**: `CitationVerifier.isFabricated()` decides what `CitationStreamingFilter` **deletes** from the live SSE stream, and its two default-ish branches both over-matched. The `unknown` kind fell through to `return true`, so every markdown link label and mermaid node name was silently removed (`[OIM docs](url)` streamed as `(url)`; `A[Start]` became `A`) — while `cleanFabricatedCitations` in the same class kept them, so the two disagreed. And `HEX_PATTERN` was `^[0-9a-fA-F]{6,32}$`, which matches ordinary English words spelled from hex letters and any 6-digit number: `[facade]`, `[decade]`, `[deadbeef]`, `[500123]` were all classified as chunk ids and deleted (`"Error code [500123] occurred."` reached the user as `"Error code  occurred."`). Both are fixed — only a 36-char uuid or 32 hex chars is a bare chunk id, matching what `thread.js` linkifies — but the lesson generalises: **deletion must be conservative, reporting can be thorough**. `checkCitations()` (advisory, feeds `verify_citations`) may flag anything suspicious; `isFabricated()` (destructive) must only remove what is provably a bad id. The reason this hid for so long is that `CitationStreamingFilterTest` mocked `CitationVerifier`, so the real classification was never executed — it even stubbed `isFabricated("[world]") → false`, which production returned `true` for. When a filter and its classifier are separate classes, test them **wired together** (`CitationStreamingFilterTest.WithRealVerifier`). The same family bit once more afterwards: a **truncated** `[chunk_id=8f7c1a2b]` was deleted from the stream *and* reported FABRICATED, even though `SectionService`/`ChunkRepository.findByIdPrefix` resolve chunks by prefix, `citation-render.js` linkifies exactly that form, and the tool's own parameter description advertised it — "not resolvable by this check" is not the same claim as "invented", so it is now `CitationStatus.UNVERIFIED` and survives the stream. Both behaviours now derive from ONE shared `classify()` plus one `shouldStrip()` predicate rather than two hand-written chains that were free to drift apart again. And note what `verify_citations` actually proves: it loads no chunk text (`findExistingIds` selects `id` only), so it confirms a cited id EXISTS and says nothing about whether the source supports the claim — the tool description and success message now say so, because "All citations resolve ✅" was read as "the answer is grounded", which is exactly wrong on a corpus where an English paraphrase can carry a real German chunk's id.
- **`verify -Pe2e-tests` silently invalidates the coverage report**: the `e2e-tests` profile reuses `@{failsafeArgLine}`, so it writes `target/jacoco-it.exec` with `append=false` — replacing the real IT coverage with e2e-only data — and the base `jacoco-merge` + `jacoco-report-aggregate` executions still run at `verify`, rewriting `target/site/jacoco-aggregate` from it. The ratchet (`jacoco-check-ratchet`) is scoped to the `it-tests` profile, so nothing fails and nothing warns: the report just quietly drops from ~81% line to roughly the unit-only figure (~52%). Diagnostic tell: aggregate coverage collapses immediately after an e2e run with no code change. Re-run `./mvnw verify -Pit-tests` before trusting, publishing or ratcheting off the local report. Harmless in CI, where `test` and `e2e` are separate jobs on separate runners with separate workspaces.
- **Re-ingesting a JSON corpus does NOT update its `json_schemas` row**: `JsonObjectService.upsertSchemaForTag` merges newly-seen fields only when `source = 'inferred'`. A hand-authored row (`source = 'imported'` / `'manual'`) is **frozen**, so an import that adds a field or a new enum value writes `json_objects` and leaves the declaration untouched — and that declaration is exactly what MCP `get_json_schema` hands the agent. Measured on `OIM - DB - History` 2026-07-26: the frozen rows declared 4 of 10 `via` values and 6 of 11 `category` values, so an agent asking about a category that existed in 760 rows was told the data does not exist. There is no warning anywhere; nothing compares the declaration to the data. Treat the declaration as a **separate deliverable from the data**: version it next to the corpus and apply it explicitly (`oim-kb/ingest/apply_json_schemas.py`). When adding a field or widening an enum in any ingested corpus, update the declaration in the same change, and check enum coverage, not just field coverage — a schema can list every field and still be wrong about all of them.

- **`chunks` partitions come from a trigger, not from the migrations — which breaks every naive `pg_dump --data-only`**: `trg_collections_create_chunks_partition` creates `chunks_p_<uuid>` when a row is inserted into `collections`, so a data-only restore only works if (a) `collections` loads **before** `chunks`, and (b) the trigger stays **enabled**. - **`ON CONFLICT` arbitrates on exactly ONE index — naming a non-PK unique column silently overwrites a different row**: an `INSERT ... ON CONFLICT (name) DO UPDATE` on a table whose PK is `id` and which also has `UNIQUE (slug)` looks like a safe upsert and is not. Postgres evaluates only the *arbiter* index before choosing INSERT vs UPDATE, so renaming a row to a **free** name finds no `name` conflict, proceeds with the real INSERT and dies on the row's own PK (`duplicate key ... _pkey`) — renaming becomes impossible; renaming to a name **another row already holds** fires the arbiter and `DO UPDATE` rewrites *that other row's entire tuple* — credentials included — then `RETURNING` hands back **the other row's id**, so the caller believes it saved the row it was editing while the row it actually edited is a different one and the original is untouched. - **A failed run rendered as "[Generation stopped by user]", and `agent_runs.error` said only "429 ."**: one incident, four independent information losses, each worth remembering separately. - **`CURRENT_TIMESTAMP` is the *transaction* start time, so a batched insert stamps every row identically — and the tie-break was a random UUID**: `MessageRepository.save` wrote `created_at = CURRENT_TIMESTAMP`, which Postgres freezes for the whole transaction (`now()`/`transaction_timestamp()` are the same function; only `clock_timestamp()` re-reads the clock per call, and `statement_timestamp()` per statement — so a multi-row `INSERT … SELECT` still ties under the latter). `DesktopSyncService.appendMessages` is `@Transactional` and posts a whole desktop turn as one batch, so the user row and the assistant row got **byte-identical** `created_at`; `findByConversationId`'s `ORDER BY created_at ASC, id ASC` then fell through to `id`, generated by `UUID.randomUUID()` — a random v4. - **Validate leniently, query strictly = a silent-empty bug: forward the *stored* value, not the caller's spelling**: two MCP tools accepted a value case-insensitively and then queried with it case-sensitively, so a caller who got the casing wrong was told the thing exists and then shown nothing. `SearchCorpusTool` matched the collection with `equalsIgnoreCase` but passed the caller's string to `ChunkRepository.resolveCollectionIds`, which is `SELECT id FROM collections WHERE name IN (:names)` — exact match — so `collection="oim"` against stored `OIM` resolved to **zero ids** and returned `(no matching chunks)`. `ListDocumentsTool` did the same with `kind`: validated via `validKinds.stream().anyMatch(knd::equalsIgnoreCase)`, then filtered with `AND d.kind = :kind`, so `kind="TABLE"` against stored `table` listed nothing. Three diagnostic levers, learned the hard way. (1) The `[DONE]` payload identifies the branch for free: `doneEvent(id, 0,0,0,0,0)` (all-zero counts) is `stream()`'s error path, whereas the controller's own catch sends a bare `[ERROR] …` + `[DONE]` with **no** JSON — so `"…[DONE] {\"messageId\":…,\"promptTokens\":0,…}"` in a response tells you exactly which handler ran. (2) In Spring 7 `ResponseBodyEmitter.send` has **no "send failed" latch** — only `complete` gates later writes — so if the inline `⚠️` notice *did* reach the client after a failed token, the failing write was non-sticky, which rules out `AsyncRequestNotUsableException` (async request COMPLETED/ERROR) and "emitter has already completed". (3) `DefaultSseEmitterHandler.send(Set)` writes `data:`, the token and `\n\n` and only *then* flushes, so a throw can leave the payload already in the response while `send()` fails — a truncated stream does **not** mean the last visible token was never written. The exception is now `SseWriteFailedException` carrying `token #N` (successful writes so far): the old `ClientGoneException` named a *diagnosis* rather than the event, and since Spring wraps every non-`IOException` from the write path into `IllegalStateException`, a transport fault with a perfectly live client was reported as a disconnect. Note also that MockMvc cannot manufacture the sticky cases: `asyncDispatch()` → `getAsyncResult()` awaits the async-dispatch latch, which only counts down via `MockAsyncContext.dispatch()` reached from `DeferredResult.setResult` inside `emitter.complete()`, so the async request cannot complete mid-stream and the assertion cannot race the stream. Finally, when writing such a stress harness: MockMvc's security filter clears `SecurityContextHolder` after every request (re-seed it before any service-level call between requests), and `/chat/*/send` is rate-limited at 20/min per `user:<auth.getName()>` — vary the OIDC `sub` per iteration rather than disabling the limiter, which would change the context key and mint a second Spring context.

Related but distinct from the sibling entries about the SDK's *own* retry policy: that one multiplies attempts, this one erases them.
- **A prompt that says "revise your previous answer" while omitting the previous answer buys a full re-research every round**: `OrchestrationService`'s review loop appended the reviewer's feedback under a `## Reviewer feedback to address (revise your previous answer)` header and passed **only** `question + feedback` — the draft was held in a local variable and never sent, and `st.evidence` is rendered exclusively into the reviewer's task, so the revising orchestrator had neither the text it was told to edit nor the material behind it. It cannot revise from that; it can only start over, which is what it did. **The loss is structural, not a decision anyone took**: every agent turn is a fresh stateless call, and `RagService.buildInitialMessages` flattens `history` down to `user`/`assistant` **content strings** — so a `tool` message, which is what every specialist result is, cannot cross that channel at all, and handing round 2 the previous message list would silently drop the evidence inside it. Evidence has to travel as rendered text, which is exactly what `st.evidence` already is; both blocks now go into the revision prompt, at about what the reviewer already pays for the same material. Measured on run `ec419a8a`, where the reviewer's *sole* objection was one mis-numbered citation: round 2 re-ran the entire specialist search at **216,667** prompt tokens to fix a reference number, the run spent **539,391** tokens against roughly half that needed, and it died `HTTP 429` on the final reviewer turn — the duplicated research is what provoked the provider's rate limit, so an unbounded-looking cost bug surfaced as an infrastructure error two steps later. The user-visible symptom is not a cost at all: the answer appears to restart from the beginning instead of finishing, which reads as a loop bug. Two lessons. **A prompt instruction that references context the prompt does not contain is silently unfollowable** — the model complies as best it can, so the failure looks like a model quality problem rather than a missing input, and nothing logs it; when adding such an instruction, assert the referenced material is actually in the rendered prompt. And **the surrounding tests documented the intent while pinning its opposite**: one javadoc stated "on a rejection the orchestrator revises rather than restarts" as settled fact and the evidence list was made cumulative to serve it, while a sibling test asserted the exact round-2 query with `isEqualTo` — encoding the draft's absence as the contract, so the suite went green on the behaviour its own comments said was wrong. A string equality assertion over a rendered prompt is a strong test of *what is there* and no test whatsoever of what is missing.
- **`history` and `priorMessages` are not two ways to do one thing — one of them cannot carry a tool-calling conversation at all**: `RagService.buildInitialMessages` maps `history` with `if ("user")… else if ("assistant")…`, using the 2-arg `LlmMessage` constructor, so **every `tool` message is dropped and every assistant message loses its `toolCalls`, `parts`, `toolCallId` and `toolName`**. That is right for replaying prior *chat* turns and silently destructive for replaying an *agent's own* transcript: hand an agent its previous message list through `history` and it gets the prose while every tool result — the evidence — vanishes, with no error and no log line. `AgenticRequest.priorMessages` exists for the second case and is taken verbatim, appending only the new user turn. Rules that come with it: the seed must already begin with a system message, because nothing adds one; `systemPromptOverride` is deliberately NOT re-applied over index 0, since the earlier turns were answering the instructions in the seed and overwriting them rewrites the question those answers belong to; and the seed is cumulative, so anything ALSO rendered into the new user turn (evidence text, the draft) is duplicated unless it is sent as a delta — `OrchestrationService` tracks `evidenceSent` for exactly that. Persisting is the mirror trap: `agent_steps.messages` stored `result.messages()` wholesale, which with a cumulative list re-stores round 1 inside round 2's row and again inside round 3's, growing the trace quadratically while showing each step work it did not do (`messagesAddedBy` now writes only the delta). One thing that needed no work: providers already round-trip this shape, because the agentic loop re-sends the whole growing list on every iteration — a longer list across rounds is structurally identical to a longer list within one.
- **`seq` allocated when a step FINISHES numbers a nested call ahead of its own parent**: a specialist runs *inside* the orchestrator's turn (`call_specialist` re-enters `runAgent` on the same thread), so it completes first, and `st.seq.incrementAndGet()` sitting after `generateAgenticAnswer` gave it the lower number. `AgentStepRepository.findByRunId` orders by `seq` with no tiebreaker, so the admin trace rendered the answer above the request that caused it — the work before the decision. Allocating at step START fixes it, with two consequences that must land in the same change: `recordFailedStep` has to REUSE the number rather than mint its own (or a failed step burns two and the gap re-orders the trace it was meant to fix), and any value derived from the counter changes meaning — `FailureContext`'s `afterSteps=N` counted completed steps and now names the failing step itself, so it was renamed `atStep=`. Note the shape of the test that hid this: the existing seq test asserted `containsExactly(1, 2, 3)` over Mockito-captured arguments, which is **insertion** order, so it passed while pinning the bug; the assertion that means anything is over the values sorted by `seq`, matching how the page reads them back. Generalise: when writes happen in a different order from the numbering that orders them, an assertion on capture order is testing the writer, not the ordering.
- **A 429 whose quota page says 0% is a shared-capacity rejection, and only the response headers can tell you — so read them**: measured live on an Azure **Global Standard** deployment of `DeepSeek-V4-Flash`: 250 RPM allocated, peak observed traffic **7 requests/minute (2.8%)**, the portal reporting *"0% rate limiting, no errors in last 7 days"*, and the app failing on `429 RateLimitReached` regardless. Global Standard is best-effort shared capacity, not reserved throughput, so a rejection can come from pool congestion without ever touching the deployment's own counter — which is why the portal and the application both told the truth while appearing to contradict each other. Request SIZE is the aggravator rather than the rule broken: a 161,835-token request **succeeded** at 06:54 (it is in `llm_call_logs`, which records only successes — failures leave no row, so never read that table as a complete request log) and comparable ones failed minutes later, so there is no fixed per-request cap to stay under, just a bigger slice of a contended pool. The body is useless for diagnosis — it says only "Your requests to X for X in westus have exceeded rate limit" — so `ProviderRateLimit` now reads `retry-after`, `x-ratelimit-remaining-tokens`, `x-ratelimit-remaining-requests` and `apim-request-id` (the id Azure support asks for) off `HttpResponseException.getResponse().getHeaders()`, feeding **one** extractor to both `LlmRetry` (backoff) and `LlmFailureSummary` (the persisted trace). Two rules come out of it. **Honour `Retry-After` instead of guessing** — `ConfluenceClientService` had done so on its own 429s since forever while the LLM path invented a 15s/30s schedule, and against shared capacity the server's interval is the only number in the exchange that means anything; clamp it (300s here) so a provider cannot park a run. And **a test over headers must vary the CASE** — the first version of `theRateLimitHeadersAreReadOffTheResponse` set every header lowercase, so swapping `equalsIgnoreCase` for `equals` left it green: it never tested the rule it existed for. HTTP/2 sends lowercase while `com.sun.net.httpserver` rewrites to `Retry-After`, so an exact-case reader is green in one environment and red in the other — the same shape that bit the `cf-aig-*` gateway headers. The fix is `HttpHeaders.getValue(HttpHeaderName.fromString(name))`, which matches case-insensitively by construction, pinned by a test that sets `Retry-After`/`X-RateLimit-Remaining-Tokens` in mixed case and was verified red against a `String.equals` reader.
- **`-DskipTests` does not skip this project's unit tests — it is a silent no-op**: `pom.xml` configures surefire with `<skipTests>${skipUnitTests}</skipTests>`, and a plugin `<configuration>` value overrides the user property of the same name, so the flag is parsed and discarded. Measured: `./mvnw -o test -DskipTests` ran all **1393** tests and ended in BUILD SUCCESS, while `-DskipUnitTests=true` prints `Tests are skipped.` and returns in seconds. This was live in `redeploy.sh --skip-tests`, whose own step banner reads "tests skipped" while the entire unit suite runs — the one flag whose whole purpose is a fast rebuild did nothing, and it went unnoticed for as long as it did precisely because the build still passed. The browser-side tier is a THIRD switch again (`-DskipJsTests=true`), bound through `exec-maven-plugin` rather than surefire, so skipping the Java tests alone still requires `node` on `PATH`. Generalises: when a pom hard-wires a plugin parameter to a project property, the standard `-D` user property for that parameter becomes inert — grep the pom for the parameter name before trusting any flag that claims to skip work, and confirm the test COUNT changed rather than reading a bare success line.
- **Rolling the migration image back is a SILENT no-op, and every forward deploy runs the previous release's code against the new schema**: two facts that invert the obvious rollback story, both verified rather than assumed. Flyway's `ignoreMigrationPatterns` defaults to `*:future` — read from the bytecode of the exact shipped `flyway/flyway:10.22.0`, whose `/flyway/conf/` contains only `flyway.toml.example`, so no config file overrides anything — and a rollback only ever drops TRAILING versions, which is exactly the FUTURE state that pattern ignores. So pointing the migration image at an older tag does not fail: Flyway warns, applies nothing, exits 0, and nothing anywhere reports that the schema is still ahead of the code. Do NOT "correct" this by clearing `ignoreMigrationPatterns`; that converts every rollback into an outage, and the genuinely loud failure — a checksum mismatch from editing an applied migration — is already forbidden. Second fact: the app Deployment declares no `strategy:`, so the RollingUpdate default surges a new pod whose migration initContainer applies the NEW schema while the PREVIOUS release's container is still serving, for as long as the startup probe and `minReadySeconds` allow. The rule that follows binds EVERY release rather than only rollbacks: **migrations must be additive-only** — new tables, new indexes, new nullable-or-defaulted columns — a destructive change is a two-release operation (stop using the object, ship that, drop it in the next), and rolling back past one is a database restore, not a redeploy.
