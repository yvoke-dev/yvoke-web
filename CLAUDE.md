# Yvoke-Web — Claude Code Project Rules

This project enforces Spec-Driven Development and strict architectural patterns.
These rules **override** default behavior. Follow them exactly.

> This file is the Claude Code equivalent of `.agents/AGENTS.md`. The two are kept
> in sync intentionally — if you change a rule here, mirror it there (and vice versa).

## 1. Universal Hard Rules (apply to ALL tasks)

- **Do NOT commit or merge**: Never commit, push, or merge via Git. The user reviews and commits manually. Leave changes uncommitted in the working tree.
- **Testing & TDD**: Use strict TDD (Red → Green → Refactor). Integration tests MUST end with `*IT.java` and live in `src/it/java`, mirroring the source package structure. Run integration tests via `./mvnw verify -Pit-tests` (requires a running Docker daemon).
- **Regression testing**: When a bug is discovered, first write a failing test (unit or integration) that reproduces it, then fix it.
- **Flyway migrations**: SQL scripts go in `docker/db/migration/` using sequential naming `V<N>__<name>.sql`. Never modify an existing migration script.
- **Vertical domain packaging**: Group Java code by domain slice under `de.palsoftware.yvoke` (never horizontal/layer-first). The dependency invariants are enforced by `ArchitectureTest.java` (ArchUnit) and fail the build on regression:
  - `shared` must not depend on **any** domain package (it is cross-cutting infrastructure only).
  - A domain's `core` must not depend on that domain's `api`/`web` (presentation depends on core, never the reverse).
  - Controllers (`@Controller`/`@RestController`) live only in `..api..`, `..web..`, or `..security..`.
  - Domain slices must be free of cycles.
  - Note: cross-domain dependencies between domains ARE allowed — a legitimate cross-domain orchestrator (e.g. `lifecycle.core`) may depend on multiple domains. Do not "fix" a domain→domain dependency unless `ArchitectureTest` actually fails.
- **DTOs at the boundary**: The service layer maps DB entities/records to DTOs before returning to the web/UI layer. Raw entities must not leak into Thymeleaf templates.
- **No inline config defaults**: Define all defaults in `application.yml`. Never use inline defaults in `@Value` (no `@Value("${x:default}")`).
- **No fully-qualified class names inline**: Add an `import` at the top of the file and use the simple name (e.g. `AtomicInteger`, not `java.util.concurrent.atomic.AtomicInteger`).
- **No assumptions**: If requirements are ambiguous, use the `AskUserQuestion` tool to present multiple-choice options before proceeding. Do not guess on design intent.
- **Self-learning**: When you hit a non-obvious pitfall or key architectural insight, record it — update this file's *Known Pitfalls* section AND `.agents/AGENTS.md`, or the relevant `.antigravity/steering/` doc, so it isn't repeated.

## 2. Engineering Standards (security · performance · maintainability)

Apply to **all** code, not just large tasks. Get it right while writing — do not defer to review.

**Security** — this is an AI/RAG app; treat request params, ingested corpus (Confluence/manuals), and LLM output as **tainted input**:
- **Parameterized SQL only.** Bind values with `JdbcClient` named/positional params. Never concatenate or interpolate request/corpus/LLM-derived values into SQL — including dynamic `ORDER BY`/`LIMIT` (whitelist those against a fixed set).
- **Authorize every entry point.** Gate controllers/endpoints with `@PreAuthorize` or the security filter chain; deny by default. Enforce the caller's ownership of the data they touch — never trust an id straight from the request.
- **Validate at the boundary.** `@Valid` + Bean Validation on all external input (REST DTOs, form posts, MCP tool args). Reject bad input; don't sanitize-and-hope.
- **Never expose secrets.** No credentials/API keys/PII in code, logs, error messages, or templates. Secrets come from env / `application.yml` placeholders only.

**Performance:**
- **No N+1.** One round-trip: batch or join in SQL; never loop a query per row.
- **Index what you filter/sort/join** — especially every FK. Use the pgvector / ParadeDB BM25 indexes on retrieval paths.
- **Read paths are `@Transactional(readOnly = true)`;** keep transactions narrow — no LLM/HTTP calls inside a DB transaction.
- **Stream, don't block.** LLM/large responses over SSE; paginate list endpoints; respect `app.worker.concurrency` for background work.
- **Cache deliberately.** `@Cacheable` (Caffeine) only for hot, stable reads, with a defined eviction key/policy.

**Maintainability:**
- Smallest change at the root cause; no speculative abstraction or "for later" config knobs.
- Names carry intent; comments explain **why**, not what; match surrounding style.
- Cross-cutting infra lives in `shared`; domain logic never does.

## 3. Tech Stack & Local Workflow

- **Backend**: Spring Boot (Java 25), PostgreSQL. Use `JdbcClient` for data access — **no ORMs**.
- **Frontend**: Thymeleaf + htmx + Vanilla CSS. **No Tailwind.**
- **Layering**: Controllers → Services → Repositories. Respect existing packages.
- **Run locally**: `./redeploy.sh` starts the app at `http://localhost:8080`. View errors with `docker compose logs app`.
- **Frontend debugging**: Drive the local server with the browser tools against `http://localhost:8080`.
- **Test tiers** (full plan in `docs/testing-plan.md`):
  - `./mvnw test` — unit tests only (fast, no Docker). Also runs the **JS tier** (below).
  - **JS tier** — `node --test src/test/js/*.test.js` (or `npm test`). Pure browser-side logic extracted from `thread.js` into `static/js/chat/citation-render.js`; tested with `node:test`, **zero dependencies** (no `npm install` — the root `package.json` exists only to declare `type: module` and the script). Bound to the `test` phase via `exec-maven-plugin`; skip with `-DskipJsTests=true`. Put string→string rendering logic here, not in e2e: it is ~1000× faster, and browser e2e **cannot** cover mermaid/KaTeX at all (both are CDN-only in `chat/layout.html` and `AbstractE2E` aborts every non-localhost request, so a diagram assertion passes whether the source is intact or destroyed).
  - `./mvnw verify -Pit-tests` — unit + integration (Testcontainers Postgres; **excludes** browser e2e). Emits the aggregated JaCoCo report (`target/site/jacoco-aggregate`) and enforces the **coverage ratchet** (fails if the merged aggregate drops below the floor). Add `-DskipUnitTests=true -Dit.test=Foo` to run one IT fast.
  - `./mvnw verify -Pe2e-tests` — Playwright browser e2e (`*E2EIT`, extend `AbstractE2E`); first run downloads Chromium to `~/.cache/ms-playwright`.
- **Mocking the LLM in tests**: replace the **provider** bean — `@MockitoBean(name = "llmProviderClient") LlmClient` — the **provider** bean, not the `@Primary` `LlmClient`, which is the `AccountingLlmClient` decorator; mocking the primary would replace cost accounting along with the provider — with `doAnswer(...)` feeding `LlmResponseChunk`s drives the whole rendered answer deterministically (no network, provider-agnostic). Browser e2e call `AbstractE2E.stubAssistantReply("…")` for a one-line scripted answer; a *blocking* `doAnswer` (latch + `Thread.sleep` → `CancellationException`) is needed to test stop/cancel. Do **not** use WireMock for answer simulation.

## 6. Known Pitfalls (project-specific)

- **Mock `HttpServer` tests**: Bind explicitly to `new InetSocketAddress("127.0.0.1", 0)` and consume `exchange.getRequestBody().readAllBytes()` before responding — otherwise you get flaky socket-closure / 400 errors from unconsumed request bodies.
- **LLM call context & FK constraints**: When logging sub-calls (embeddings/reranks/tools) during an in-flight LLM turn, set `LlmCallContextHolder` with the already-persisted `userMessageId` to avoid `fk_llm_call_logs_messages` FK violations before the assistant message exists.
- **Background-thread user resolution**: Background / virtual threads have no `SecurityContext`. Resolve `user_id` via `conversationRepository.findById(convId).map(Conversation::userId)`, not `SecurityContextHolder`.
- **Thymeleaf inline-JS script order**: In templates with `th:inline="javascript"`, declare all `const`/`let` (DOM selectors, state arrays) near the top of the script block, before any top-level function invocation — otherwise page init throws a Temporal Dead Zone (TDZ) `ReferenceError`.
- **Dev-profile is required for mock auth & plaintext secrets (fail-closed)**: `app.security.mock=true` and running without `APP_SECRET_KEY` are only permitted when a `dev`/`local`/`test` profile is active (`SecurityConfig`/`SecretCipher` throw at startup otherwise — SEC-09/SEC-05). The IT harness activates `test` via `PostgresTestContainerInitializer`; local `docker-compose` sets `SPRING_PROFILES_ACTIVE=local`. A new `@SpringBootTest` in `src/it` inherits `test` automatically; a full-context test elsewhere with `mock=true` must set the profile itself.
- **`@Component` with two constructors won't autowire**: If a bean exposes both a `@Value`/production constructor and a package-private test-seam constructor, annotate the production one with `@Autowired` — otherwise Spring can't choose and fails context startup with "No default constructor found" (only surfaces in ITs, not plain unit tests, so always run `./mvnw verify -Pit-tests` after adding such a class).
- **`@ControllerAdvice(annotations = Controller.class)` also matches `@RestController`**: `@RestController` is meta-annotated with `@Controller`, so an MVC-only advice selected by `annotations = Controller.class` (e.g. `MvcExceptionHandler`) is *also* applicable to REST controllers and would compete with the JSON `ApiExceptionHandler`. Give the REST advice higher precedence (`@Order(Ordered.HIGHEST_PRECEDENCE)`) so it wins for `@RestController`s; the MVC advice (`LOWEST_PRECEDENCE`) then only reaches plain `@Controller`s. When a global MVC error advice redirects, gate it to *classic browser form posts* (state-changing method + `Accept: text/html` + no `HX-Request`/`X-Requested-With`) and re-throw everything else, or it will hijack htmx fragments, `void`/`@ResponseBody` fetch endpoints, downloads and GET renders. Re-emit `ResponseStatusException` via `response.sendError(status, reason)` (don't let the generic `Exception` handler swallow it) so a 404 stays a 404 instead of becoming a redirect.
- **IT context-cache thrash poisons the `RANDOM_PORT` MCP context**: The `src/it` suite has more distinct `@SpringBootTest` contexts than Spring's default TestContext cache (`maxSize=32`). Adding an IT whose config is *distinct* (a new `properties`/`@MockitoBean`/mock-bean combination mints a new context) tips it over; LRU eviction + recreation of `McpServerEndpointsIT`'s `RANDOM_PORT` context leaves the spring-ai MCP server poisoned — the JSON-RPC `initialize` POST returns **400**. Diagnostic tell: the new IT passes **alone and in pairs**, but the *full* `./mvnw verify -Pit-tests` fails in an **unrelated** `RANDOM_PORT` IT. Fix is `src/it/resources/spring.properties` → `spring.test.context.cache.maxSize=64`. When adding ITs, prefer **reusing an existing context** (identical annotations/properties/mock beans) over minting a new one; if a full-suite failure surfaces in an unrelated `RANDOM_PORT` IT, suspect cache size, not that IT.
- **All ingest staging must live under `app.upload-dir`**: the worker-side `UploadPathGuard` rejects any job `sourceRef` outside `app.upload-dir`, so staging an upload with `Files.createTempDirectory(...)` (system tmp) makes the job fail at *execution* time with "sourceRef resolves outside the permitted upload directory" — the enqueue succeeds, so nothing surfaces until the worker runs. Stage with `Files.createTempDirectory(Path.of(uploadDir)…, prefix)` and pin it with a unit test asserting the enqueued `sourceRef` starts with the upload root.
- **Ingest tags are silently dropped when the target collection declares no tags**: `CollectionTagEnqueueValidator` only validates/propagates the request's `tag` when `collections.tags` is non-empty — against a collection created with `tags='{}'` the job runs untagged, documents lose version scoping, and a second version's ingest *replaces* the first (same `source_file` keys). Declare the allowed tags on the collection (e.g. `{9.3.1,10.0}`) *before* the first ingest.
- **Graph identity is `(collection, kind, lower(name), tag set)` — the tag is part of it (V2)**: the OIM corpus keeps two kit versions in ONE collection separated only by tag. While identity was tag-blind, the second version's ingest resolved every same-named entity to the FIRST version's row, `appendTags`'d its tag onto it and inserted nothing; since the per-version document link lives in `entities.metadata->>'document_id'` and nothing ever UPDATEd an existing row, **9,431 of 10.0's 9,904 entities kept pointing at 9.3.1's documents** while the job reported 9,904 written. The read paths were never wrong — they already filter `:tag = ANY(tags)` — the shared row simply carried both tags and had one document_id to give. Consequences to respect: the unique index is over `kg_canonical_tags(tags)` (an IMMUTABLE `COLLATE "C"` sort/dedup, so array ORDER can never fork one scope into two) and every `ON CONFLICT` must name that exact expression; `KgWriteRepository.entityKey` deliberately stays two-part `kind:name` because three call sites parse it positionally (one upsert call = one tag set = one scope); **never reintroduce `appendTags`** — welding a second tag onto an existing row IS the bug; `KgConsolidator` must keep `kg_canonical_tags(e.tags)` in its GROUP BY and edge-collapse PARTITION BY, or it re-merges the split and hard-DELETEs one row, cascading its edges away; and a name+kind without a tag is now ambiguous exactly like a name without a kind, so ordering must be total and the MCP tools return the candidate versions instead of merging them.
- **Re-ingest orphans an entity's `document_id` unless the upsert refreshes it**: `CustomIngestService` deletes and recreates every document with a NEW uuid on each run, but entity rows survive. `upsertEntitiesBatch` had no update branch at all, so a re-ingested collection's entities pointed at deleted documents. `refreshResolved` now writes `metadata`/`description`/`embedding` onto rows resolved in the same tag scope, with `COALESCE` so the LLM path (`DocumentIngestService.persistGraph`, 3-arg `EntityUpsert` with null metadata) cannot wipe the document link the custom path wrote.
- **Graph/document identity is `(collection, kind, name)` — a name alone is ambiguous**: in `OIM - Custom - Install Kit` ~945 entity names and ~900 document titles exist under two to five kinds (`Person` is a `table`, an `entity_model`, `ui_forms`, `object_methods` *and* a `notification`; a REST provider's full name is usually both an `api` and an `api_server`; every colliding connector name also names a `module`). Consequences to respect in any name-based lookup: order rows by a **total** order (a name+similarity tie is otherwise resolved non-deterministically by Postgres, so the caller silently gets a different `document_id` per call), surface `kind` in every tool output, and make an ambiguous lookup fail loudly rather than merging kinds (`get_graph_neighbors` returns the candidate kinds + edge counts instead of edges when no `kind` is given). Prompts/playbooks must pass `kind` alongside `entity_name` and take `document_id` from the row with that kind.
- **Custom (jsonl) ingest fails the job; kg-extract only reports**: `CustomIngestService` now THROWS `IllegalStateException` (which `JobService` turns into the job's `error`, so it reaches the user) on unparseable YAML frontmatter, on any graph entity that resolves to no document, and on an unresolvable edge endpoint (unknown / ambiguous-across-kinds / malformed record) — each message names the offenders, capped at the first 20 plus a total. The trigger was real: a `display_name: %Globals...%` starts a plain YAML scalar with the reserved `%` indicator, so the frontmatter failed to parse, the document silently degraded to `kind='other'`, and its `table` entity ended up with **no `document_id`** for two full re-ingests. `DocumentIngestService.persistGraph` (LLM extraction) deliberately does NOT throw — its entities always come from the document being ingested, and one stray model-invented name must not kill a whole kg-extract job — so it reports the loss instead via `JobCounts.skippedEntities/skippedEdges` (persisted by `V4`, shown on the job-detail page). When adding a new fixture zip to `CustomIngestServiceIT`, give **every** entity in `graph/entities.jsonl` a markdown file with matching `kind`+`name`, or the job legitimately fails.
- **A `<script type="module">` is deferred, so a classic inline script cannot call into it at load time**: the admin pages keep classic inline scripts (their runtime-cloned `<template>` rows carry inline `on*=` handlers that resolve globally and break under module scope), and extracted logic is bridged in via a tiny module script that assigns `window.X`. Module scripts are **always deferred** — they execute *after* every classic script but *before* `DOMContentLoaded`. So a top-level `togglePrompts();` at the end of the classic script runs while `window.IngestForm` is still `undefined` and throws `TypeError: Cannot read properties of undefined`. Function *definitions* and event handlers are fine (they run later); only immediate init calls break. Fix: wrap the init call in `document.addEventListener('DOMContentLoaded', …)`. Check for this with `grep -nE '^ {4,12}[a-zA-Z_$][a-zA-Z0-9_$]*\([^)]*\);[[:space:]]*$'` on the template before extracting — `ingest.html` and `job-detail.html` both had one. `AdminPagesConsoleE2EIT` catches it (it asserts no uncaught JS errors across every admin page), but only if the page is in its list.
- **Bracketed text is not automatically a citation — over-matching deletes the user's prose**: `CitationVerifier.isFabricated()` decides what `CitationStreamingFilter` **deletes** from the live SSE stream, and its two default-ish branches both over-matched. The `unknown` kind fell through to `return true`, so every markdown link label and mermaid node name was silently removed (`[OIM docs](url)` streamed as `(url)`; `A[Start]` became `A`) — while `cleanFabricatedCitations` in the same class kept them, so the two disagreed. And `HEX_PATTERN` was `^[0-9a-fA-F]{6,32}$`, which matches ordinary English words spelled from hex letters and any 6-digit number: `[facade]`, `[decade]`, `[deadbeef]`, `[500123]` were all classified as chunk ids and deleted (`"Error code [500123] occurred."` reached the user as `"Error code  occurred."`). Both are fixed — only a 36-char uuid or 32 hex chars is a bare chunk id, matching what `thread.js` linkifies — but the lesson generalises: **deletion must be conservative, reporting can be thorough**. `checkCitations()` (advisory, feeds `verify_citations`) may flag anything suspicious; `isFabricated()` (destructive) must only remove what is provably a bad id. The reason this hid for so long is that `CitationStreamingFilterTest` mocked `CitationVerifier`, so the real classification was never executed — it even stubbed `isFabricated("[world]") → false`, which production returned `true` for. When a filter and its classifier are separate classes, test them **wired together** (`CitationStreamingFilterTest.WithRealVerifier`). The same family bit once more afterwards: a **truncated** `[chunk_id=8f7c1a2b]` was deleted from the stream *and* reported FABRICATED, even though `SectionService`/`ChunkRepository.findByIdPrefix` resolve chunks by prefix, `citation-render.js` linkifies exactly that form, and the tool's own parameter description advertised it — "not resolvable by this check" is not the same claim as "invented", so it is now `CitationStatus.UNVERIFIED` and survives the stream. Both behaviours now derive from ONE shared `classify()` plus one `shouldStrip()` predicate rather than two hand-written chains that were free to drift apart again. And note what `verify_citations` actually proves: it loads no chunk text (`findExistingIds` selects `id` only), so it confirms a cited id EXISTS and says nothing about whether the source supports the claim — the tool description and success message now say so, because "All citations resolve ✅" was read as "the answer is grounded", which is exactly wrong on a corpus where an English paraphrase can carry a real German chunk's id.
- **`verify -Pe2e-tests` silently invalidates the coverage report**: the `e2e-tests` profile reuses `@{failsafeArgLine}`, so it writes `target/jacoco-it.exec` with `append=false` — replacing the real IT coverage with e2e-only data — and the base `jacoco-merge` + `jacoco-report-aggregate` executions still run at `verify`, rewriting `target/site/jacoco-aggregate` from it. The ratchet (`jacoco-check-ratchet`) is scoped to the `it-tests` profile, so nothing fails and nothing warns: the report just quietly drops from ~81% line to roughly the unit-only figure (~52%). Diagnostic tell: aggregate coverage collapses immediately after an e2e run with no code change. Re-run `./mvnw verify -Pit-tests` before trusting, publishing or ratcheting off the local report. Harmless in CI, where `test` and `e2e` are separate jobs on separate runners with separate workspaces.
- **Re-ingesting a JSON corpus does NOT update its `json_schemas` row**: `JsonObjectService.upsertSchemaForTag` merges newly-seen fields only when `source = 'inferred'`. A hand-authored row (`source = 'imported'` / `'manual'`) is **frozen**, so an import that adds a field or a new enum value writes `json_objects` and leaves the declaration untouched — and that declaration is exactly what MCP `get_json_schema` hands the agent. Measured on `OIM - DB - History` 2026-07-26: the frozen rows declared 4 of 10 `via` values and 6 of 11 `category` values, so an agent asking about a category that existed in 760 rows was told the data does not exist. There is no warning anywhere; nothing compares the declaration to the data. Treat the declaration as a **separate deliverable from the data**: version it next to the corpus and apply it explicitly (`oim-kb/ingest/apply_json_schemas.py`). When adding a field or widening an enum in any ingested corpus, update the declaration in the same change, and check enum coverage, not just field coverage — a schema can list every field and still be wrong about all of them.
- **`docker compose up -d` never rebuilds — a new migration or code change is silently absent**: `docker/db/Dockerfile` is `COPY docker/db/migration/ /flyway/sql/` and the app `Dockerfile` copies `target/*.jar`, so both are **baked into images**. `docker compose up -d app` reuses them; a migration written since the last `docker compose build`, and every source change since the last Maven build, is simply not running — while the stack starts cleanly and Flyway reports success. Observed live: `V2__graph_identity_includes_tag_set.sql` sat on disk unapplied, the running jar predated the whole F4 change set (`0` occurrences of `kg_canonical_tags`), and a single-version ingest passed **every** validation because one tag scope has nothing to merge with; the second version would have reproduced the original bug in full. Diagnostic tell: `docker logs yvoke-db-migration | grep 'Successfully validated'` reports fewer migrations than `ls docker/db/migration/`, and `select version from flyway_schema_history` lags the newest file. Use `./redeploy.sh` (mvn → `docker compose build` → down/up), and **assert the schema version before any ingest whose correctness depends on a migration** — the app will not tell you.
- **A timed-out `./mvnw` run keeps running and poisons the next build**: when an invocation exceeds an agent tool timeout it is *detached, not killed* — the Maven JVM, its surefire/failsafe fork, the Playwright driver and headless Chromium all survive (observed still alive after 2h) and keep writing `target/`. The next build shares that directory and the symptom is baffling: tests fail at **runtime** with `Unresolved compilation problems: AbstractE2E cannot be resolved to a type` while `./mvnw test-compile` on the very same sources reports BUILD SUCCESS. Deleting `target/test-classes` makes it go away for one run, which sends you chasing a phantom stale-artifact bug. The real check is `ps -eo pid,etime,command | grep -E 'mvnw|surefire|playwright'` for a second long-running build; kill the tree with `-TERM`, then `-9` for the surefire fork and Playwright driver, which routinely ignore `-TERM`. Orphaned Testcontainers are reaped by Ryuk once the client connection drops, so don't `docker rm` them by hand — and never touch the long-lived `yvoke-app` + pgvector pair, which is the local `docker compose` stack from `./redeploy.sh`.
- **`chunks` partitions come from a trigger, not from the migrations — which breaks every naive `pg_dump --data-only`**: `trg_collections_create_chunks_partition` creates `chunks_p_<uuid>` when a row is inserted into `collections`, so a data-only restore only works if (a) `collections` loads **before** `chunks`, and (b) the trigger stays **enabled**. Both of the reflexes here are wrong: `pg_dump` orders data blocks alphabetically, which puts `chunks` first (FK violation *and* no partition to route into), and the standard data-only remedy — `--disable-triggers` / `session_replication_role = replica` — suppresses the very trigger that builds the partitions. FK safety must come from the table **order** instead: one `pg_dump` per table concatenated in topological order, with partitioned tables dumped via `--load-via-partition-root` so each `COPY` targets the parent and the target routes rows itself. A third trap sat underneath: V1 defined `create_chunks_partition()` with an unqualified `chunks` and no pinned `search_path`, while every `pg_dump` preamble emits `set_config('search_path', '', false)` — so the restore died mid-`collections` with `ERROR: no schema has been selected to create in` (SQLSTATE 3F000). `V1__init_schema.sql` now defines the function schema-qualified *and* with `SET search_path = public, pg_temp`; `SchemaPresenceIT.testCollectionInsertManagesPartitionWithEmptySearchPath` pins it. Working scripts live in `/Users/eduardpal/work/yvoke-icc/yvoke-backups/scripts` (see the README one level up) — use them rather than re-deriving the flags. They cover both environments off one switch (`YVOKE_ENV=local|netcup`, docker exec vs `kubectl exec` into the CNPG pod) and produce **schema-only + data-only** rather than a full dump plus a data-only dump, which stored the same 1.6 GB of rows twice; the schema file (~170 KB) carries the DDL, the `chunks` partitions — which no migration contains — and the `flyway_schema_history` **rows**, so the pair restores to exactly what the full dump did. Restore with `restore-into.sh` (schema from the dump, no Flyway) when the dump does not match `docker/db/migration`, which is the normal case for a netcup dump: the two environments are not always on the same migration. The older `/Users/eduardpal/work/yvoke/backup/scripts` set is superseded. The import script runs Flyway via the `db-migration` compose service rather than piping the SQL through psql: psql builds the same schema but leaves `flyway_schema_history` empty, so the next `docker compose up` tries to build it again and fails. Also exclude `flyway_schema_history` from data-only dumps: Flyway writes it when the target is migrated, and replaying the rows collides on its PK.
- **`ON CONFLICT` arbitrates on exactly ONE index — naming a non-PK unique column silently overwrites a different row**: an `INSERT ... ON CONFLICT (name) DO UPDATE` on a table whose PK is `id` and which also has `UNIQUE (slug)` looks like a safe upsert and is not. Postgres evaluates only the *arbiter* index before choosing INSERT vs UPDATE, so renaming a row to a **free** name finds no `name` conflict, proceeds with the real INSERT and dies on the row's own PK (`duplicate key ... _pkey`) — renaming becomes impossible; renaming to a name **another row already holds** fires the arbiter and `DO UPDATE` rewrites *that other row's entire tuple* — credentials included — then `RETURNING` hands back **the other row's id**, so the caller believes it saved the row it was editing while the row it actually edited is a different one and the original is untouched. A third unique column (`slug`) is never arbitrated at all and surfaces as a raw 23505. Verified live on `confluence_instances` in a rolled-back transaction: saving A under B's name returned B's id, overwrote B's domain and **blanked B's `api_token_enc`/`token_key_id`**. Always arbitrate on the **primary key** (`ON CONFLICT (id)`) and let the other unique constraints raise 23505 for the controller to map; add an explicit `findByName`/`findBySlug` for callers that need "create-or-adopt". - **A custom `OkHttpClient` makes the genai SDK silently drop every `HttpOptions` transport setting**: `ApiClient.createHttpClient` (google-genai 1.60.0, `ApiClient.java:279-314`) branches on `clientOptions.customHttpClient()`. The *else* branch builds its own client and applies `connectTimeout(0)`/`readTimeout(0)`/`writeTimeout(0)`, `httpOptions.timeout() -> callTimeout(...)`, the `Dispatcher` (`maxConnections`/`maxConnectionsPerHost`) and `proxyOptions`. The *custom* branch is one line — `builder = customClient.get().newBuilder();` — so **none** of that is applied and the client keeps OkHttp 4.x defaults: **10s connect / 10s read / 10s write, no call timeout**. `GeminiLlmClient` asks for `HttpOptions.timeout(300_000)`, but `CloudflareGeminiLlmClient` always supplies a custom client (it needs the interceptor for `cf-aig-metadata`), and `app.ai.provider` defaults to `cloudflare-gemini` — so *every* environment ran on a 10s read timeout, and any thinking model taking >10s to emit its first SSE token died with `SocketTimeoutException`. There is no warning: `HttpOptions.timeout()` is accepted and ignored. The fix is that a custom client must reproduce what the SDK would have configured — `GeminiLlmClient.HTTP_TIMEOUT_MS` is now the single source both sites read. Pin it with a test that reflects to the real client (`GeminiLlmClient.client` -> `Client.apiClient` -> public `ApiClient.httpClient()`) and asserts the four timeouts, with the plain `GeminiLlmClient` as the control — asserting on getters is fast and deterministic, where a true behavioural test would have to stall >10s. Generalise the lesson: **supplying a custom transport to any SDK means you inherit responsibility for all of its transport config**, and `maxConnections`/`proxyOptions` are still dropped on this path today — they are simply unset, so nothing breaks yet.
- **A failed run rendered as "[Generation stopped by user]", and `agent_runs.error` said only "429 ."**: one incident, four independent information losses, each worth remembering separately. (1) **The client invented a status the server never reported.** `thread.js`'s async poll passed `status === 'error'` into `finalizeStream`'s `isAborted` parameter, which means *the user pressed Stop* — so every failure was captioned as a cancellation underneath the generic system error. Reaching that line is positive proof the user did NOT stop (all three `signal.aborted` guards `return` first). The rule now enforced by `pollTerminalDecision` in `thread-text.js`: **the client never invents status text for a message the server has already authored**, and anything that is not `generating` is terminal — an unrecognised status used to match no branch at all, which left the poll re-arming via `setTimeout` forever with the loader interval never cleared. (2) **Cancel and failure were the same status.** `ChatMessageService` wrote `"error"` from *both* its `CancellationException` and its generic `Exception` catch, so nothing downstream could tell them apart; `messages.status` is unconstrained TEXT and nothing filters on `'error'`, so adding `'cancelled'` needed no migration — but `ChatAsyncController`'s terminal branch was a bare `else` mapping every non-`generating` status to `"done"`, which must be fixed in the same change or a cancelled run reports as a finished answer. (3) **`ApiException.getMessage()` is `String.format("%d %s. %s", code, status, message)`**, and against the Cloudflare AI Gateway both trailing fields are empty (OkHttp exposes no HTTP/2 reason phrase; the SDK only parses Google's own `{"error":{"message":…}}` shape) — so the message really is the string `"429 . "`, `code()` is the only informative field, and persisting bare `e.getMessage()` yields an unusable record. `LlmFailureSummary` decodes it; anything persisted from an exception must also be redacted (bearer tokens, `key=`/`api_key=`/`access_token=`) and length-capped, because an exception message is arbitrary third-party text. (4) **Failure context is frame-local and vanishes.** `agent_steps` rows were inserted only *after* a successful call, so the two calls that actually failed left no row; and `runOrchestration` resolved its profile and playbooks *before* the run row existed, so a missing playbook produced no `agent_runs` row at all. Both now record. Two traps when writing these records: a `CancellationException` arrives as a thread interrupt, so clear it around the JDBC write (`Thread.interrupted()`, restore after) or the record is silently lost; and a remembered failure context must be matched to the exception that actually ends the run (identity check), or a specialist failure the orchestrator recovered from will confidently mislabel a later, unrelated error.
- **The genai SDK retries *inside* every `LlmRetry` attempt — the two layers multiply**: `ApiClient.createHttpClient` adds `new RetryInterceptor(retryOptions)` **outside** its custom-vs-default `if/else` (unlike every timeout setting, which only the else branch applies), so supplying a custom `OkHttpClient` does *not* opt out of it. Its default is `RETRY_MAX_ATTEMPTS = 5` on exactly the codes `LlmRetry.isTransient` retries (408/429/500/502/503/504), so our 3 attempts were really **up to 15 HTTP requests**, each re-uploading a ~600k-token prompt into the quota that had just returned 429 — which is why every "attempt" took 35–46s and the window never reset. `HttpOptions.retryOptions(HttpRetryOptions.builder().attempts(1).build())` now pins the SDK to one attempt so `LlmRetry` is the single retry authority, and 429 gets a quota-scale backoff (15s base, 60s cap) instead of the 500ms used for ordinary blips. Pin this with a test that reflects into the interceptor (`OkHttpClient.interceptors()` → `RetryInterceptor.retryOptions`); asserting on `HttpOptions` alone would not catch the branch. Generalises the sibling pitfall below: **supplying a custom transport means inheriting responsibility for the SDK's transport config — and auditing what the SDK applies regardless.**
- **A tool result is model input, so it is a SEC-17 surface**: `RagService.executeToolCalls` handed the model `"Error: " + e.getMessage()` on a tool failure. Tool results are appended to the conversation, and in orchestrated mode the orchestrator's synthesised text *becomes* the user-visible answer — so provider/exception detail there can be paraphrased straight past `GENERIC_ERROR_TEXT`. - **The cost dashboard re-prices from tokens, so fixing `llm_call_logs.total_cost` alone changes nothing on screen**: `CostCalculationService.getFilteredExplorerReport` never reads the persisted `total_cost` — all three view levels (RAW/MESSAGE/CONVERSATION) call `getModelCost(model, p, c, ca, t, dbPrices)` and re-derive cost from the stored token counts at *current* rates. - **Cloudflare AI Gateway caching is ON, and it caches SSE**: verified live against the production gateway (`docker exec yvoke-app printenv` for credentials, two byte-identical requests). With no `cf-aig-cache-ttl` header from the app — caching is enabled at the gateway/dashboard level, not in code — the second `:generateContent` returned `cf-aig-cache-status: HIT`, and so did the second `:streamGenerateContent?alt=sse`. Both assumptions people reach for are wrong: it is not off, and streaming is not exempt. The cache key is `SHA-256(provider + endpoint + model + auth header + full request body)`, so organic chat rarely repeats — but the *first* turn of a new conversation is a small stable body, and **an eval harness replaying a fixed question set sends byte-identical first turns by design**: those runs can be scored against a replayed answer while the model never executes, and their cost figures are wrong in the same direction. Send `cf-aig-skip-cache: true` on eval traffic. Note also that the headers are readable without any interceptor: the genai SDK exposes them on `GenerateContentResponse.sdkHttpResponse()` and stamps them onto *every* streamed chunk (`ResponseStream`), so `LlmGatewayInfo` is read as a local variable next to `usageMetadata` — no ThreadLocal, no threading assumption. Header-name lookup must be case-insensitive: HTTP/2 sends lowercase but `com.sun.net.httpserver` rewrites to `Cf-aig-…`, so an exact-case match is green in production and red in tests.

- **`./mvnw test-compile` can silently skip edited test sources — a TDD "red" run then reports BUILD SUCCESS**: after editing several test files to call methods that did not exist yet, `./mvnw -o test-compile` printed `Nothing to compile - all classes are up to date` for both `default-compile` and `default-testCompile` and exited 0, so the red phase looked green and the missing API looked like it already existed. `touch`ing the sources did not help. - **`CURRENT_TIMESTAMP` is the *transaction* start time, so a batched insert stamps every row identically — and the tie-break was a random UUID**: `MessageRepository.save` wrote `created_at = CURRENT_TIMESTAMP`, which Postgres freezes for the whole transaction (`now()`/`transaction_timestamp()` are the same function; only `clock_timestamp()` re-reads the clock per call, and `statement_timestamp()` per statement — so a multi-row `INSERT … SELECT` still ties under the latter). `DesktopSyncService.appendMessages` is `@Transactional` and posts a whole desktop turn as one batch, so the user row and the assistant row got **byte-identical** `created_at`; `findByConversationId`'s `ORDER BY created_at ASC, id ASC` then fell through to `id`, generated by `UUID.randomUUID()` — a random v4. Each turn therefore rendered user-first or assistant-first **by coin flip**, and stably so, because `messages_conversation_created_idx (conversation_id, created_at, id)` matches the ORDER BY exactly, so every read reproduces the same wrong order. Measured on production 2026-08-05: **11 of 11** desktop turns tied, **7** rendered backwards; conversation `d919ccc0` showed all three answers above their questions. The web chat path was never affected — `ChatMessageService` has no `@Transactional` there, so the user save and the assistant-placeholder save are separate transactions and get different timestamps; the function was never wrong, it was used across a boundary it does not cross. Fix is `clock_timestamp()` in the INSERT (one word, no migration, fixes every caller of `save`). Two lessons that generalise: **a random-UUID tie-break is not a tie-break** — it converts a timestamp collision into silent data corruption rather than a stable fallback, so any `ORDER BY t, id` over v4 ids is only as good as `t`'s uniqueness; and this is not cosmetic, because `DesktopSyncService.getMessages` feeds `AppCore.getMessages` rehydration (reinstall / second device) which calls `replaceMessages`, writing the scrambled log locally where it becomes LLM conversation history. Sibling tables were audited and are clean: `agent_steps` carries an explicit `seq` column and orders by it (the robust pattern — prefer it when insert order *is* the semantics), and `llm_call_logs` has no `@Transactional`, so each call lands in its own transaction. Regression test: `DesktopSyncServiceIT.appendMessagesPreservesBatchOrderWithDistinctTimestamps` posts an **eight**-message batch rather than two — a two-row order assertion passes ~50% of the time pre-fix, eight rows only 1-in-8!, and the strictly-increasing-`createdAt` assertion is the deterministic anchor that fails on every pre-fix run (observed red: `["a4","a1","q2","a2","q4","q1","q3","a3"]`).
