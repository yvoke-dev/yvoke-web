# Yvoke-Web Project Rules

This project enforces Spec-Driven Development (ASDD) and strict architectural patterns.

## 1. Universal Hard Rules (Apply to ALL tasks)
- **Do NOT Commit**: Never commit, push, or merge changes via Git. The user reviews and commits manually. Leave changes uncommitted in the working tree.
- **Testing & TDD**: Use strict TDD (Red-Green-Refactor). Integration tests MUST end with `*IT.java` and be placed in `src/it/java` mirroring the source package structure. Run tests via `./mvnw verify -Pit-tests` (requires Docker daemon).
- **Flyway Migrations**: SQL scripts MUST go in `docker/db/migration/` using sequential naming `V<N>__<name>.sql`. Never modify existing scripts.
- **Vertical Domain Packaging**: Java code must be grouped by domain slices under `de.palsoftware.yvoke` (never horizontal packages). The invariants enforced by `ArchitectureTest.java` (ArchUnit) are: `shared` must not depend on any domain; a domain's `core` must not depend on its own `api`/`web`; controllers only in `api`/`web`/`security`; slices free of cycles. Cross-domain dependencies between domains ARE permitted (e.g. a `lifecycle.core` orchestrator) — do not refactor one away unless `ArchitectureTest` actually fails.
- **DTOs at the Boundary**: The service layer maps DB entities/records to DTOs before returning to the web/UI layer. Raw entities must not leak into Thymeleaf templates.
- **No Inline Config Defaults**: Define all defaults in `application.yml`. Never use inline defaults in `@Value` (no `@Value("${x:default}")`).
- **No Assumptions**: If requirements are ambiguous, use the native `ask_question` tool to present multiple-choice options to clarify implementation details. Do not proceed with assumptions.
- **Regression Testing**: Whenever an issue or bug is discovered, write a failing test (unit or integration) that reproduces the problem before fixing it to prevent future regressions.
- **Self-Learning & Knowledge Sharing**: When mistakes, non-obvious pitfalls, or key architectural/domain insights are discovered during a task, update `.agents/AGENTS.md` (or steering documents in `.antigravity/steering/`) so the team and agent do not repeat the same mistake.
- **No Fully-Qualified Class Names**: Do not use inline fully-qualified class names in Java code (e.g., `java.util.concurrent.atomic.AtomicInteger`). Instead, add an import statement at the top of the file and use the simple class name (e.g., `AtomicInteger`).

## 2. Engineering Standards (security · performance · maintainability)

Apply to **all** code, not just large tasks. Get it right while writing — do not defer to review.

**Security** — this is an AI/RAG app; treat request params, ingested corpus (Confluence/manuals), and LLM output as **tainted input**:
- **Parameterized SQL only.** Bind values with `JdbcClient` named/positional params. Never concatenate or interpolate request/corpus/LLM-derived values into SQL — including dynamic `ORDER BY`/`LIMIT` (whitelist those against a fixed set).
- **Authorize every entry point.** Gate controllers/endpoints with `@PreAuthorize` or the security filter chain; deny by default. Enforce the caller's ownership of the data they touch — never trust an id straight from the request.
- **Validate at the boundary.** `@Valid` + Bean Validation on all external input (REST DTOs, form posts, MCP tool args). Reject bad input; don't sanitize-and-hope.
- **Never expose secrets.** No credentials/API keys/PII in code, logs, error messages, or templates. Secrets come from env / `application.yml` placeholders only.

**Performance:**
- **No N+1.** One round-trip: batch or join in SQL; never loop a query per row.
- **Index what you filter/sort/join** — especially every FK. Use the pgvector / ParadeDB BM25 indexes on retrieval paths.
- **Read paths are `@Transactional(readOnly = true)`;** keep transactions narrow — no LLM/HTTP calls inside a DB transaction.
- **Stream, don't block.** LLM/large responses over SSE; paginate list endpoints; respect `app.worker.concurrency` for background work.
- **Cache deliberately.** `@Cacheable` (Caffeine) only for hot, stable reads, with a defined eviction key/policy.

**Maintainability:**
- Smallest change at the root cause; no speculative abstraction or "for later" config knobs.
- Names carry intent; comments explain **why**, not what; match surrounding style.
- Cross-cutting infra lives in `shared`; domain logic never does.

## 3. Task Routing & Subagents
- **Small/Medium Tasks**: Execute directly. No planning artifacts required.
- **Large Tasks**: You MUST use the Spec-Driven Development (ASDD) flow. Read `file://./.antigravity/sdd_protocol.md` before starting.
- **Available Subagents**: 
  - `spring_implementer`: Writes local Spring Boot/Postgres code.
  - `spring_reviewer`: Audits code for security/performance.
  - *Rule*: Define subagents via `define_subagent` using the templates in `.antigravity/agents/`. Only ONE code-writing subagent may be active at any given time.

## 4. Tech Stack & Debugging
- **Backend**: Use `JdbcClient` for data access (no ORMs).
- **Frontend**: Use Thymeleaf, htmx, and Vanilla CSS (no Tailwind).
- **Local Server**: Run `./redeploy.sh` to start the app. The server runs at `http://localhost:8080`. Use `docker compose logs app` to view server errors.
- **Frontend Debugging**: Use the `chrome-devtools-mcp` server to automate browser testing on the local server URL.
- **Test tiers** (full plan in `docs/testing-plan.md`): `./mvnw test` = unit only (fast, no Docker) **plus the JS tier**; `./mvnw verify -Pit-tests` = unit + IT (Testcontainers, **excludes** `*E2EIT`), emits the aggregated JaCoCo report (`target/site/jacoco-aggregate`) and enforces the **coverage ratchet** (fails below the floor) — add `-DskipUnitTests=true -Dit.test=Foo` for one IT; `./mvnw verify -Pe2e-tests` = Playwright browser e2e (`*E2EIT`, extend `AbstractE2E`; first run downloads Chromium).
- **JS tier**: `node --test src/test/js/*.test.js` (or `npm test`). Pure browser-side logic extracted from `thread.js` into `static/js/chat/citation-render.js`, tested with `node:test` and **zero dependencies** (the root `package.json` only declares `type: module`; no `npm install`). Bound to the Maven `test` phase via `exec-maven-plugin`; skip with `-DskipJsTests=true`. Put string→string rendering logic here rather than in e2e — it is ~1000× faster, and e2e **cannot** cover mermaid/KaTeX at all (CDN-only in `chat/layout.html`, and `AbstractE2E` aborts non-localhost requests, so those assertions pass even when the source is destroyed).
- **Mocking the LLM in tests**: replace the **provider** bean via `@MockitoBean(name = "llmProviderClient") LlmClient` — the **provider** bean, not the `@Primary` `LlmClient`, which is the `AccountingLlmClient` decorator; mocking the primary would replace cost accounting along with the provider + `doAnswer(...)` feeding `LlmResponseChunk`s (deterministic, provider-agnostic, no network). Browser e2e call `AbstractE2E.stubAssistantReply("…")`; testing stop/cancel needs a *blocking* `doAnswer` (latch + `Thread.sleep` → `CancellationException`). Do NOT use WireMock for answer simulation.
- **Mock HttpServer Testing**: When writing tests with `com.sun.net.httpserver.HttpServer`, always bind explicitly to `new InetSocketAddress("127.0.0.1", 0)` and consume `exchange.getRequestBody().readAllBytes()` before sending the response to avoid unconsumed request body race conditions and flaky socket closure / 400 errors.
- **LLM Call Context & FK Constraints**: When logging sub-calls (embeddings/reranks/tools) during in-flight LLM turns, set `LlmCallContextHolder` with `userMessageId` (which is already persisted in `messages`) to avoid `fk_llm_call_logs_messages` foreign key violations prior to assistant message creation.
- **Background Thread User Resolution**: Background or virtual threads lack SecurityContext. To resolve `user_id` reliably for LLM logging or orchestration, query `conversationRepository.findById(convId).map(Conversation::userId)` rather than relying on `SecurityContextHolder`.
- **Thymeleaf & Inline JS Script Order**: In Thymeleaf templates with `th:inline="javascript"`, place all `const` / `let` variable declarations (such as DOM selectors or state arrays) near the top of the script block before top-level function invocations, avoiding Temporal Dead Zone (TDZ) `ReferenceError` crashes on page initialization.
- **A `<script type="module">` is deferred — a classic inline script cannot call into it at load time**: admin pages keep classic inline scripts (their runtime-cloned `<template>` rows carry inline `on*=` handlers that resolve globally and break under module scope), with extracted logic bridged in by a tiny module script assigning `window.X`. Module scripts always execute AFTER every classic script but BEFORE `DOMContentLoaded`, so a top-level init call like `togglePrompts();` throws `TypeError: Cannot read properties of undefined`. Definitions and event handlers are fine; only immediate calls break. Wrap init in `DOMContentLoaded`. Grep the template for bare top-level calls before extracting — `ingest.html` and `job-detail.html` both had one; `AdminPagesConsoleE2EIT` catches it if the page is in its list.
- **Bracketed text is not automatically a citation — over-matching deletes the user's prose**: `CitationVerifier.isFabricated()` decides what `CitationStreamingFilter` **deletes** from the live SSE stream, and both of its loose branches over-matched. The `unknown` kind fell through to `return true`, silently removing every markdown link label and mermaid node name (`[OIM docs](url)` streamed as `(url)`; `A[Start]` became `A`) while `cleanFabricatedCitations` in the same class kept them — the two disagreed. And `HEX_PATTERN` was `^[0-9a-fA-F]{6,32}$`, which matches English words spelled from hex letters and any 6-digit number, so `[facade]`, `[decade]`, `[deadbeef]` and `[500123]` were classified as chunk ids and deleted. Both fixed (only a 36-char uuid or 32 hex chars is a bare chunk id, matching `thread.js`), but the rule generalises: **deletion must be conservative, reporting can be thorough** — `checkCitations()` (advisory, feeds `verify_citations`) may flag anything suspicious; `isFabricated()` (destructive) must only remove what is provably a bad id. It hid for so long because `CitationStreamingFilterTest` mocked `CitationVerifier`, so the real classification never ran — it even stubbed `isFabricated("[world]") → false`, which production returned `true` for. Test a filter **wired to its real classifier** (`CitationStreamingFilterTest.WithRealVerifier`). The same family bit once more afterwards: a **truncated** `[chunk_id=8f7c1a2b]` was deleted from the stream *and* reported FABRICATED, even though `SectionService`/`ChunkRepository.findByIdPrefix` resolve chunks by prefix, `citation-render.js` linkifies exactly that form, and the tool's own parameter description advertised it — "not resolvable by this check" is not the same claim as "invented", so it is now `CitationStatus.UNVERIFIED` and survives the stream. Both behaviours now derive from ONE shared `classify()` plus one `shouldStrip()` predicate rather than two hand-written chains free to drift apart again. And note what `verify_citations` actually proves: it loads no chunk text (`findExistingIds` selects `id` only), so it confirms a cited id EXISTS and says nothing about whether the source supports the claim — the tool description and success message now say so, because "All citations resolve ✅" was read as "the answer is grounded", which is exactly wrong on a corpus where an English paraphrase can carry a real German chunk's id.
- **Dev-profile required for mock auth & plaintext secrets (fail-closed)**: `app.security.mock=true` and running without `APP_SECRET_KEY` are only permitted when a `dev`/`local`/`test` profile is active — `SecurityConfig`/`SecretCipher` throw at startup otherwise (SEC-09/SEC-05). The IT harness activates `test` (`PostgresTestContainerInitializer`); local `docker-compose` sets `SPRING_PROFILES_ACTIVE=local`.
- **`@Component` with two constructors won't autowire**: A bean exposing both a `@Value`/production constructor and a package-private test-seam constructor must annotate the production one with `@Autowired`, or context startup fails with "No default constructor found" — a failure that only shows up in ITs, so run `./mvnw verify -Pit-tests` after adding such a class.
- **`@ControllerAdvice(annotations = Controller.class)` also matches `@RestController`**: `@RestController` is meta-annotated with `@Controller`, so an MVC-only advice (`MvcExceptionHandler`) also applies to REST controllers and competes with the JSON `ApiExceptionHandler`. Give the REST advice `@Order(Ordered.HIGHEST_PRECEDENCE)` so it wins for `@RestController`s; the MVC advice (`LOWEST_PRECEDENCE`) then only reaches plain `@Controller`s. A global MVC error advice that redirects must gate on *classic browser form posts* (state-changing + `Accept: text/html` + no `HX-Request`/`X-Requested-With`) and re-throw everything else, or it hijacks htmx fragments, `void`/`@ResponseBody` fetch endpoints, downloads and GET renders; re-emit `ResponseStatusException` via `response.sendError(status, reason)` so a 404 stays a 404 rather than becoming a redirect.
- **IT context-cache thrash poisons the `RANDOM_PORT` MCP context**: The `src/it` suite has more distinct `@SpringBootTest` contexts than Spring's default TestContext cache (`maxSize=32`). Adding an IT with a *distinct* config (a new `properties`/`@MockitoBean`/mock-bean combination mints a new context) tips it over; LRU eviction + recreation of `McpServerEndpointsIT`'s `RANDOM_PORT` context leaves the spring-ai MCP server poisoned — the JSON-RPC `initialize` POST returns **400**. Tell-tale: the new IT passes **alone and in pairs**, but the *full* `./mvnw verify -Pit-tests` fails in an **unrelated** `RANDOM_PORT` IT. Fix is `src/it/resources/spring.properties` → `spring.test.context.cache.maxSize=64`. Prefer **reusing an existing context** (identical annotations/properties/mock beans) when adding ITs; if a full-suite failure surfaces in an unrelated `RANDOM_PORT` IT, suspect cache size, not that IT.
- **All ingest staging must live under `app.upload-dir`**: the worker-side `UploadPathGuard` rejects any job `sourceRef` outside `app.upload-dir`, so staging an upload with `Files.createTempDirectory(...)` (system tmp) makes the job fail at *execution* time with "sourceRef resolves outside the permitted upload directory" — the enqueue succeeds, so nothing surfaces until the worker runs. Stage with `Files.createTempDirectory(Path.of(uploadDir)…, prefix)` and pin it with a unit test asserting the enqueued `sourceRef` starts with the upload root.
- **Ingest tags are silently dropped when the target collection declares no tags**: `CollectionTagEnqueueValidator` only validates/propagates the request's `tag` when `collections.tags` is non-empty — against a collection created with `tags='{}'` the job runs untagged, documents lose version scoping, and a second version's ingest *replaces* the first (same `source_file` keys). Declare the allowed tags on the collection (e.g. `{9.3.1,10.0}`) *before* the first ingest.
- **Graph identity is `(collection, kind, lower(name), tag set)` — the tag is part of it (V2)**: the OIM corpus keeps two kit versions in ONE collection separated only by tag. While identity was tag-blind, the second version's ingest resolved every same-named entity to the FIRST version's row, `appendTags`'d its tag onto it and inserted nothing; since the per-version document link lives in `entities.metadata->>'document_id'` and nothing ever UPDATEd an existing row, **9,431 of 10.0's 9,904 entities kept pointing at 9.3.1's documents** while the job reported 9,904 written. The read paths were never wrong — they already filter `:tag = ANY(tags)` — the shared row simply carried both tags and had one document_id to give. Consequences to respect: the unique index is over `kg_canonical_tags(tags)` (an IMMUTABLE `COLLATE "C"` sort/dedup, so array ORDER can never fork one scope into two) and every `ON CONFLICT` must name that exact expression; `KgWriteRepository.entityKey` deliberately stays two-part `kind:name` because three call sites parse it positionally (one upsert call = one tag set = one scope); **never reintroduce `appendTags`** — welding a second tag onto an existing row IS the bug; `KgConsolidator` must keep `kg_canonical_tags(e.tags)` in its GROUP BY and edge-collapse PARTITION BY, or it re-merges the split and hard-DELETEs one row, cascading its edges away; and a name+kind without a tag is now ambiguous exactly like a name without a kind, so ordering must be total and the MCP tools return the candidate versions instead of merging them.
- **Re-ingest orphans an entity's `document_id` unless the upsert refreshes it**: `CustomIngestService` deletes and recreates every document with a NEW uuid on each run, but entity rows survive. `upsertEntitiesBatch` had no update branch at all, so a re-ingested collection's entities pointed at deleted documents. `refreshResolved` now writes `metadata`/`description`/`embedding` onto rows resolved in the same tag scope, with `COALESCE` so the LLM path (`DocumentIngestService.persistGraph`, 3-arg `EntityUpsert` with null metadata) cannot wipe the document link the custom path wrote.
- **Graph/document identity is `(collection, kind, name)` — a name alone is ambiguous**: in `OIM - Custom - Install Kit` ~945 entity names and ~900 document titles exist under two to five kinds (`Person` is a `table`, an `entity_model`, `ui_forms`, `object_methods` *and* a `notification`; a REST provider's full name is usually both an `api` and an `api_server`; every colliding connector name also names a `module`). Consequences to respect in any name-based lookup: order rows by a **total** order (a name+similarity tie is otherwise resolved non-deterministically by Postgres, so the caller silently gets a different `document_id` per call), surface `kind` in every tool output, and make an ambiguous lookup fail loudly rather than merging kinds (`get_graph_neighbors` returns the candidate kinds + edge counts instead of edges when no `kind` is given). Prompts/playbooks must pass `kind` alongside `entity_name` and take `document_id` from the row with that kind.
- **Custom (jsonl) ingest fails the job; kg-extract only reports**: `CustomIngestService` now THROWS `IllegalStateException` (which `JobService` turns into the job's `error`, so it reaches the user) on unparseable YAML frontmatter, on any graph entity that resolves to no document, and on an unresolvable edge endpoint (unknown / ambiguous-across-kinds / malformed record) — each message names the offenders, capped at the first 20 plus a total. The trigger was real: a `display_name: %Globals...%` starts a plain YAML scalar with the reserved `%` indicator, so the frontmatter failed to parse, the document silently degraded to `kind='other'`, and its `table` entity ended up with **no `document_id`** for two full re-ingests. `DocumentIngestService.persistGraph` (LLM extraction) deliberately does NOT throw — its entities always come from the document being ingested, and one stray model-invented name must not kill a whole kg-extract job — so it reports the loss instead via `JobCounts.skippedEntities/skippedEdges` (persisted by `V4`, shown on the job-detail page). When adding a new fixture zip to `CustomIngestServiceIT`, give **every** entity in `graph/entities.jsonl` a markdown file with matching `kind`+`name`, or the job legitimately fails.
- **Re-ingesting a JSON corpus does NOT update its `json_schemas` row**: `JsonObjectService.upsertSchemaForTag` merges newly-seen fields only when `source = 'inferred'`. A hand-authored row (`source = 'imported'` / `'manual'`) is **frozen**, so an import that adds a field or a new enum value writes `json_objects` and leaves the declaration untouched — and that declaration is exactly what MCP `get_json_schema` hands the agent. Measured on `OIM - DB - History` 2026-07-26: the frozen rows declared 4 of 10 `via` values and 6 of 11 `category` values, so an agent asking about a category that existed in 760 rows was told the data does not exist. There is no warning anywhere; nothing compares the declaration to the data. Treat the declaration as a **separate deliverable from the data**: version it next to the corpus and apply it explicitly (`oim-kb/ingest/apply_json_schemas.py`). When adding a field or widening an enum in any ingested corpus, update the declaration in the same change, and check enum coverage, not just field coverage — a schema can list every field and still be wrong about all of them.

## 6. Known Pitfalls (project-specific)

Accumulated, hard-won gotchas live in `CLAUDE.md` § 6 — Spring TestContext cache thrash, ingest staging paths,
kind-aware graph identity, the `@ControllerAdvice` precedence trap, JaCoCo/e2e report clobbering, and detached
Maven runs corrupting `target/`. Read that section before debugging a build or test failure that makes no sense;
several entries exist specifically because the obvious diagnosis was the wrong one.

Kept as a pointer rather than a copy: the list is long and changes often, and two divergent copies would be worse
than one. Add new entries there, not here.
- **`ON CONFLICT` arbitrates on exactly ONE index — naming a non-PK unique column silently overwrites a different row**: an `INSERT ... ON CONFLICT (name) DO UPDATE` on a table whose PK is `id` and which also has `UNIQUE (slug)` looks like a safe upsert and is not. Postgres evaluates only the *arbiter* index before choosing INSERT vs UPDATE, so renaming a row to a **free** name finds no `name` conflict, proceeds with the real INSERT and dies on the row's own PK — renaming becomes impossible; renaming to a name **another row already holds** fires the arbiter and `DO UPDATE` rewrites *that other row's entire tuple* — credentials included — then `RETURNING` hands back **the other row's id**, so the caller believes it saved the row it was editing. A third unique column is never arbitrated at all and surfaces as a raw 23505. Verified live on `confluence_instances`: saving A under B's name returned B's id, overwrote B's domain and **blanked B's `api_token_enc`/`token_key_id`**. Always arbitrate on the **primary key** (`ON CONFLICT (id)`) and let the other unique constraints raise 23505 for the controller to map; add an explicit `findByName`/`findBySlug` for callers that need "create-or-adopt". Related: an upsert must never write half of a paired column set — `api_token_enc` and `token_key_id` have to move together, or the row's derived health status lies.
- **A custom `OkHttpClient` makes the genai SDK silently drop every `HttpOptions` transport setting**: `ApiClient.createHttpClient` (google-genai 1.60.0, `ApiClient.java:279-314`) branches on `clientOptions.customHttpClient()`. The *else* branch applies `connectTimeout(0)`/`readTimeout(0)`/`writeTimeout(0)`, `httpOptions.timeout() -> callTimeout(...)`, the `Dispatcher` and `proxyOptions`. The *custom* branch is one line — `builder = customClient.get().newBuilder();` — so none of it is applied and OkHttp 4.x defaults stand: **10s connect / 10s read / 10s write, no call timeout**. `GeminiLlmClient` asks for `HttpOptions.timeout(300_000)`, but `CloudflareGeminiLlmClient` always supplies a custom client (needed for the `cf-aig-metadata` interceptor) and `app.ai.provider` defaults to `cloudflare-gemini` — so every environment ran on a 10s read timeout and any thinking model taking >10s to emit its first SSE token died with `SocketTimeoutException`. `HttpOptions.timeout()` is accepted and ignored, with no warning. A custom client must reproduce what the SDK would have configured; `GeminiLlmClient.HTTP_TIMEOUT_MS` is the single source both sites read. Pin it by reflecting to the real client (`GeminiLlmClient.client` -> `Client.apiClient` -> public `ApiClient.httpClient()`) and asserting the four timeouts, with plain `GeminiLlmClient` as the control. Generalise: **supplying a custom transport to any SDK means inheriting responsibility for all of its transport config** — `maxConnections`/`proxyOptions` are still dropped on this path, they are just unset today.
- **A failed run rendered as "[Generation stopped by user]", and `agent_runs.error` said only "429 ."**: one incident, four independent information losses, each worth remembering separately. (1) **The client invented a status the server never reported.** `thread.js`'s async poll passed `status === 'error'` into `finalizeStream`'s `isAborted` parameter, which means *the user pressed Stop* — so every failure was captioned as a cancellation underneath the generic system error. Reaching that line is positive proof the user did NOT stop (all three `signal.aborted` guards `return` first). The rule now enforced by `pollTerminalDecision` in `thread-text.js`: **the client never invents status text for a message the server has already authored**, and anything that is not `generating` is terminal — an unrecognised status used to match no branch at all, which left the poll re-arming via `setTimeout` forever with the loader interval never cleared. (2) **Cancel and failure were the same status.** `ChatMessageService` wrote `"error"` from *both* its `CancellationException` and its generic `Exception` catch, so nothing downstream could tell them apart; `messages.status` is unconstrained TEXT and nothing filters on `'error'`, so adding `'cancelled'` needed no migration — but `ChatAsyncController`'s terminal branch was a bare `else` mapping every non-`generating` status to `"done"`, which must be fixed in the same change or a cancelled run reports as a finished answer. (3) **`ApiException.getMessage()` is `String.format("%d %s. %s", code, status, message)`**, and against the Cloudflare AI Gateway both trailing fields are empty (OkHttp exposes no HTTP/2 reason phrase; the SDK only parses Google's own `{"error":{"message":…}}` shape) — so the message really is the string `"429 . "`, `code()` is the only informative field, and persisting bare `e.getMessage()` yields an unusable record. `LlmFailureSummary` decodes it; anything persisted from an exception must also be redacted (bearer tokens, `key=`/`api_key=`/`access_token=`) and length-capped, because an exception message is arbitrary third-party text. (4) **Failure context is frame-local and vanishes.** `agent_steps` rows were inserted only *after* a successful call, so the two calls that actually failed left no row; and `runOrchestration` resolved its profile and playbooks *before* the run row existed, so a missing playbook produced no `agent_runs` row at all. Both now record. Two traps when writing these records: a `CancellationException` arrives as a thread interrupt, so clear it around the JDBC write (`Thread.interrupted()`, restore after) or the record is silently lost; and a remembered failure context must be matched to the exception that actually ends the run (identity check), or a specialist failure the orchestrator recovered from will confidently mislabel a later, unrelated error.
- **The genai SDK retries *inside* every `LlmRetry` attempt — the two layers multiply**: `ApiClient.createHttpClient` adds `new RetryInterceptor(retryOptions)` **outside** its custom-vs-default `if/else` (unlike every timeout setting, which only the else branch applies), so supplying a custom `OkHttpClient` does *not* opt out of it. Its default is `RETRY_MAX_ATTEMPTS = 5` on exactly the codes `LlmRetry.isTransient` retries (408/429/500/502/503/504), so our 3 attempts were really **up to 15 HTTP requests**, each re-uploading a ~600k-token prompt into the quota that had just returned 429 — which is why every "attempt" took 35–46s and the window never reset. `HttpOptions.retryOptions(HttpRetryOptions.builder().attempts(1).build())` now pins the SDK to one attempt so `LlmRetry` is the single retry authority, and 429 gets a quota-scale backoff (15s base, 60s cap) instead of the 500ms used for ordinary blips. Pin this with a test that reflects into the interceptor (`OkHttpClient.interceptors()` → `RetryInterceptor.retryOptions`); asserting on `HttpOptions` alone would not catch the branch. Generalises the sibling pitfall below: **supplying a custom transport means inheriting responsibility for the SDK's transport config — and auditing what the SDK applies regardless.**
- **A tool result is model input, so it is a SEC-17 surface**: `RagService.executeToolCalls` handed the model `"Error: " + e.getMessage()` on a tool failure. Tool results are appended to the conversation, and in orchestrated mode the orchestrator's synthesised text *becomes* the user-visible answer — so provider/exception detail there can be paraphrased straight past `GENERIC_ERROR_TEXT`. The model-facing string is now provider-neutral and the diagnosis goes to the log and `agent_steps.error` instead. Related: `CallSpecialistTool.call` wrapped `handler.apply(...)` — an entire nested specialist run — in the same `try` as its `objectMapper.readValue`, so a 429 was logged as "Failed to parse call_specialist arguments" and *returned* as a normal tool result, after which `RagService` logged the call as having executed successfully. The line to hold: **the model can correct its own arguments; it cannot correct a 429** — parse/validation errors are returned strings, infrastructure failures throw.
- **The cost dashboard re-prices from tokens, so fixing `llm_call_logs.total_cost` alone changes nothing on screen**: `CostCalculationService.getFilteredExplorerReport` never reads persisted `total_cost` — all three view levels re-derive cost from stored token counts at *current* rates via `getModelCost(...)`. Write path and read path are therefore two independent cost implementations. Gateway cache accounting hit this exactly: `LlmCallLoggingService` billed a replayed call at $0 while the dashboard kept charging full price. Both now consult `gateway_cache_status` (carried by `EXPLORER_CALL_SELECT`, and in the `GROUP BY` of `explorerConversationRows` so each grouped row is uniformly replayed or not). **Any new rule about what a call costs must be applied in BOTH services**, or it is half-implemented — and the tell is a ledger/dashboard disagreement that nothing checks.
- **Cloudflare AI Gateway caching is ON and it caches SSE**: verified live with two byte-identical requests; the app sends no `cf-aig-cache-ttl` (caching is a gateway-level setting), yet the second `:generateContent` AND the second `:streamGenerateContent?alt=sse` both returned `cf-aig-cache-status: HIT`. Cache key is `SHA-256(provider + endpoint + model + auth header + full request body)`, so organic chat rarely repeats — but **an eval harness replaying a fixed question set sends byte-identical first turns by design**, so eval runs can score a replayed answer with the model never executing. Use `cf-aig-skip-cache: true` for eval traffic. The headers need no interceptor: the genai SDK exposes them on `GenerateContentResponse.sdkHttpResponse()` and stamps them onto every streamed chunk. Header-name lookup must be case-insensitive — HTTP/2 sends lowercase, `com.sun.net.httpserver` rewrites to `Cf-aig-…`, so exact-case matching is green in prod and red in tests.
- **A registry table that only *some* writers update is a silent lie — derive the vocabulary instead**: the admin tag dropdowns read a `tags` table whose only writer was `TagRepository.getOrCreateTag`, called from `addTagTo{Collection,Document,Conversation}`. So a tag was recorded exactly when it arrived through an admin form or the ingest enqueue, and never when a writer set the `TEXT[]` column directly — which is what the corpus import does (`yvoke-exports/lib/objects.py`: `INSERT INTO collections … ON CONFLICT … tags = EXCLUDED.tags`), and what every ingest service does for documents/chunks/entities/relationships/json_objects. Measured live: the registry held **2** names (`content`, `schema`) while `10.0` and `9.3.1` sat on **27 collections, 22,162 documents, 155,276 chunks, 21,510 entities, 55,677 relationships** — so two whole kit versions were unfilterable in the corpus browser and unsuggestable everywhere, with no error anywhere. The tell is a dropdown that is *short* rather than wrong, which reads as "there are only two tags" instead of "the list is stale". `V6__drop_tags_registry.sql` drops it: nothing had an FK to or from it and `tags.id` was never read, so it was pure duplicated truth. The vocabulary is now derived — `CollectionRepository.findAllTagNames()` (`SELECT DISTINCT unnest(tags) FROM collections`, 0.05 ms over 31 rows; the `documents` equivalent is a 22k-row scan at 10 ms that no index can serve and would hide a declared-but-not-yet-ingested tag) and, for chat folders, `ChatConversationService.distinctTags` over the conversations the sidebar already loaded. Two follow-on rules. **Namespaces must not share a vocabulary source**: one registry fed both corpus tags and chat folder names, so the folder autocomplete offered `9.3.1`/`10.0` and leaked every user's folder names; they are separate derivations now. And **a scoped filter must always contain its own active value** — `DocumentAdminController.tagOptions` appends `selectedTag` when the collection does not declare it, because `th:selected="${t == selectedTag}"` otherwise renders "All Tags" over a query that is still filtered, and rows vanish with no visible cause. Note the pattern was already right everywhere else (ingest/search/connectors via `getVersionOptions`, json-objects, the KG-extract dialog, the MCP tools all read `Collection::tags`); the corpus browser was the last registry reader.
- **`./mvnw test-compile` can silently skip edited test sources — a TDD "red" run then reports BUILD SUCCESS**: after editing several test files to call methods that did not exist yet, `./mvnw -o test-compile` printed `Nothing to compile - all classes are up to date` for both `default-compile` and `default-testCompile` and exited 0, so the red phase looked green and the missing API looked like it already existed. `touch`ing the sources did not help. The compiler plugin's incremental check compares against `target/test-classes` and had gone stale (the `.class` timestamp was *newer* than the `.java`). Deleting the affected package directories under `target/test-classes` produced the expected `cannot find symbol` wall immediately. So: **never read a bare BUILD SUCCESS as proof the new test actually ran** — confirm the test count changed, or `rm -rf` the relevant `target/*-classes` subtree first. Related to, but distinct from, the orphaned-`mvnw` pitfall below: there the stale `target/` comes from a second live build, here from the plugin's own up-to-date check.
- **`CURRENT_TIMESTAMP` is the *transaction* start time, so a batched insert stamps every row identically — and the tie-break was a random UUID**: `MessageRepository.save` wrote `created_at = CURRENT_TIMESTAMP`, which Postgres freezes for the whole transaction (`now()`/`transaction_timestamp()` are the same function; only `clock_timestamp()` re-reads the clock per call, and `statement_timestamp()` per statement — so a multi-row `INSERT … SELECT` still ties under the latter). `DesktopSyncService.appendMessages` is `@Transactional` and posts a whole desktop turn as one batch, so the user row and the assistant row got **byte-identical** `created_at`; `findByConversationId`'s `ORDER BY created_at ASC, id ASC` then fell through to `id`, generated by `UUID.randomUUID()` — a random v4. Each turn therefore rendered user-first or assistant-first **by coin flip**, and stably so, because `messages_conversation_created_idx (conversation_id, created_at, id)` matches the ORDER BY exactly, so every read reproduces the same wrong order. Measured on production 2026-08-05: **11 of 11** desktop turns tied, **7** rendered backwards; conversation `d919ccc0` showed all three answers above their questions. The web chat path was never affected — `ChatMessageService` has no `@Transactional` there, so the user save and the assistant-placeholder save are separate transactions and get different timestamps; the function was never wrong, it was used across a boundary it does not cross. Fix is `clock_timestamp()` in the INSERT (one word, no migration, fixes every caller of `save`). Two lessons that generalise: **a random-UUID tie-break is not a tie-break** — it converts a timestamp collision into silent data corruption rather than a stable fallback, so any `ORDER BY t, id` over v4 ids is only as good as `t`'s uniqueness; and this is not cosmetic, because `DesktopSyncService.getMessages` feeds `AppCore.getMessages` rehydration (reinstall / second device) which calls `replaceMessages`, writing the scrambled log locally where it becomes LLM conversation history. Sibling tables were audited and are clean: `agent_steps` carries an explicit `seq` column and orders by it (the robust pattern — prefer it when insert order *is* the semantics), and `llm_call_logs` has no `@Transactional`, so each call lands in its own transaction. Regression test: `DesktopSyncServiceIT.appendMessagesPreservesBatchOrderWithDistinctTimestamps` posts an **eight**-message batch rather than two — a two-row order assertion passes ~50% of the time pre-fix, eight rows only 1-in-8!, and the strictly-increasing-`createdAt` assertion is the deterministic anchor that fails on every pre-fix run (observed red: `["a4","a1","q2","a2","q4","q1","q3","a3"]`).
